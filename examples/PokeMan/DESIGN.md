# PokeMan / 口袋从者 概念设计

> 状态：Draft
>
> 本文档是 PokeMan（中文名：口袋从者）的持续概念设计文档。后续关于游戏世界、核心循环、角色关系、角色卡、口袋陪伴、成长、战斗、叙事与 MVP 的讨论，优先在本文档中逐步收敛和完善。

## 项目定位

**PokeMan** 是游戏英文名，中文名为 **口袋从者**。

口袋从者是 LoomRealm 中的一个独立 RPG 游戏实例，也是一个通过真实游戏开发持续检验 LoomRealm Core 与 `game-libs` 可用性的长期产品项目。

游戏在体验结构上对标 GBA 时代的宝可梦 RPG：以俯视角 Tile Map 探索为主要世界空间，通过地图角色、事件与 Dialogue 推进 RPG 内容，并通过独立 Battle 进入战斗体验。

但口袋从者不复刻传统宝可梦的角色关系与战斗控制。玩家扮演 **主公**，在世界中认识、接触、影响并最终收服不同角色，使其成为能够通过角色卡随身携带、持续互动并用于 Battle 的 **从者**。

Battle 是 PokeMan 与传统 Pokémon 体验形成差异化的核心系统之一。战斗中的从者不是等待玩家逐步遥控的棋子，而是具有自身判断的角色；Battle 通过 Decision / LLM 产生战术行为，并由 Simulation 决定行为是否合法、何时发生以及实际结果。未来主公通过战术指令影响从者的 Decision，而不是绕过 Decision 直接控制 Simulation。

架构与库的验证服务于真实游戏开发，而不是反过来让游戏成为技术演示或测试夹具。设计首先回答“这是否让口袋从者成为更成立的游戏”，然后再观察真实产品压力如何推动 LoomRealm 演进。

PokeMan 初期使用用户本地提供的 `essentials-v21.1` 地图与美术资源作为 GBA 风格 RPG 内容基础。项目自身主要提供游戏逻辑、配置、Dialogue / Event、Battle 定义和构建 / 适配方式；不把原版素材作为 PokeMan 自身的分发内容。

## 素材来源、构建与分发边界

PokeMan 当前计划以 **非商业发布** 为前提，并把 Pokémon / Pokémon Essentials 素材与 PokeMan 自身代码、规则和内容定义分离。

公开项目主要提供：

- PokeMan 游戏逻辑；
- 配置；
- Dialogue / Event；
- Battle 定义；
- PokeMan 自己的角色、关系与世界状态定义；
- 从 `essentials-v21.1` 映射到 PokeMan Content 的规则；
- 本地 Builder / Import tooling。

用户在自己的本地环境中提供一份可用的 `essentials-v21.1`，构建流程再生成本地可运行的 PokeMan Game Package：

```text
PokeMan source / definitions
          +
用户本地 essentials-v21.1
          ↓
PokeMan Builder / Importer
          ↓
选择、转换并映射所需 Map / Graphics / Content
          ↓
用户本地可运行的 PokeMan Game Package
```

因此项目边界是：

> **PokeMan 分发自己的游戏逻辑和构建手段；原版 Pokémon / Essentials 素材由用户本地提供，并在用户环境中参与构建。**

生成出来的素材与派生 Game Package 属于本地构建产物，不应因为开发 PokeMan 而反向把原版资源提交到项目仓库。

具体 importer 校验、版本识别、资源映射格式、输出目录和构建命令属于后续工程设计；产品设计只固定“用户本地提供原版内容，PokeMan 本身不捆绑分发原版素材”这一边界。

## 核心角色关系

- **主公**：某段契约关系中持有并组织对方角色卡的一方。玩家在自己的主要冒险视角中首先以主公身份探索、交互、选择、收服、携带与组织从者。
- **从者**：某段契约关系中被角色卡代表、能够被对方随身连接并调用力量的一方。一个人可以在一段关系中是从者，同时在另一段关系中是主公。
- **角色卡**：角色与另一方建立正式关系后，用于表达该角色身份、契约、持续连接、口袋陪伴和力量调用的可持有媒介。
- **口袋从者**：被某位主公通过角色卡随身携带、能够持续陪伴和互动的已建立正式关系角色。
- **好感度 / 关系**：描述人与人之间的关系进展，影响 Dialogue、事件、收服、挑战、战术协作和后续成长。

**主公 / 从者首先是关系位置，而不是固定职业、阶级、物种或永久身份。**

因此同一个角色可以同时：

```text
作为 A 的从者
+
作为 B、C 的主公
+
继续拥有自己的世界身份与生活
```

玩家仍然以“成为主公、认识并收服从者”作为主要收集视角，但玩家本人并不因此被排除在角色卡体系之外。

从者不是一开始就属于玩家的战斗单位。玩家需要在世界中真正认识角色，并通过 Dialogue、Event、Battle、选择和共同经历推进关系。

因此，“收服从者”的核心含义不是统一执行一次捕获动作，而是把：

```text
认识角色
→ 建立关系
→ 经历事件 / 冲突 / 挑战
→ 获得角色认可
→ 建立正式关系
→ 获得代表该角色的角色卡
```

组织成角色自己的 RPG 内容。

获得角色卡也不是角色内容的结束。角色本体继续存在于世界中，同时可以成为持卡者随身携带和调用的口袋从者。

### 双向契约可以真实成立

一段剧情可以让双方分别建立代表对方的角色卡，而不是把其中一张解释为临时教学道具。

例如序章中：

```text
玩家获得：宿敌角色卡
宿敌获得：玩家角色卡
```

这表示双方都真实进入对方的契约网络：玩家可以通过宿敌卡持续连接并调用宿敌的力量；宿敌同样持有代表玩家的角色卡，并可以在 Battle 中调用玩家的战斗化身。

双向契约不会让双方本体消失，也不会抹除任何一方作为主公的能力。

玩家自己的角色卡是否在序章之后成为一个可以持续主动分发的完整长期系统，目前仍保留两种可能：

1. **剧情限制型**：序章双向契约真实成立，但后续通过剧情、制度或能力条件限制玩家继续向其他角色分发自己的角色卡；
2. **通用角色卡型**：玩家自己的角色卡与其他角色遵循同一套世界规则，可以在满足关系条件后交给其他人物。

如果采用第二种方向，则其他角色持有玩家角色卡以后，理论上也可以：

- 与玩家的口袋化身进行 Dialogue / Interaction；
- 在 Battle 中调用玩家的战斗化身；
- 让玩家通过这条持续连接感知或事后了解本体未直接经历的信息；
- 使“谁携带谁、谁通过谁认识世界”成为双向甚至网络化的角色关系内容。

这些长期能力目前只确认其设计可能性，具体分发条件、持卡数量、权限、信息同步方式和是否允许多人同时持有同一角色的卡尚未确定。

## 核心玩法结构

当前确认的三个主要能力是：

- **Map**：承载 RPG 世界、移动、地点、NPC、角色、遭遇和空间关系。
- **Dialogue**：承载角色交流、玩家选择、关系变化、角色事件、随行互动和世界信息。
- **Battle**：承载冲突、挑战、切磋、敌对遭遇和成长，并将结果返回 RPG 世界。

其中：

> **Map + Dialogue 构成主要 RPG 世界体验，Battle 构成主要战斗体验。**

基础长期循环为：

```text
在中心管理角色卡 / 选择本次随身从者
      ↓
探索世界（Map）
      ↓
看见并接触角色 / Encounter Entity / Event
      ↓
Dialogue / Interaction
      ↓
关系变化 / Event / Challenge / Hostile Encounter
      ↓
Battle（可选或强制，取决于情境）
      ↓
结果返回角色与世界状态
      ↓
满足某个角色的收服条件
      ↓
获得角色卡并进入中心管理体系
      ↓
编入有限的随身角色卡位
      ↓
Pocket Dialogue / Event / Battle
      ↓
训练 + 关系深化 + 战术协作
      ↓
继续探索或返回中心调整随身角色卡
```

`Map`、`Dialogue` 和 `Battle` 是支持产品实现的能力，不是产品本身。真正的游戏体验来自角色、关系、陪伴、事件、旅行、战斗、成长、收服与选择。

## 角色卡与收服

### 角色卡是正式关系的结果，不是统一捕获过程

对于玩家“收服从者”的主要视角，角色卡首先表示：

- 玩家已经与该角色建立正式关系；
- 该角色进入玩家可以组织、携带和使用的角色集合；
- 主公可以与该角色保持持续连接；
- 主公可以在 Battle 中调用该角色的战斗力量；
- 角色原有的世界身份、职业、关系和剧情不会因此消失。

角色卡并不只允许单向存在。序章已经确认双方可以分别持有代表对方的角色卡；因此“获得某人的卡”表达的是一条具体关系成立，而不是把对方变成永远只能作为从者存在的人。

玩家不是通过“使用空白卡 → 捕获判定”获得所有人物。

不同角色可以拥有完全不同的收服路线：

- **关系型**：多次 Dialogue、正确选择和关系推进后主动认可主公；
- **挑战型**：需要 Battle 证明实力；
- **事件型**：完成角色自己的地图或剧情事件；
- **复合型**：Dialogue、Event、Battle、多次相遇组合；
- **条件型**：要求特定地点、世界状态、已拥有角色或其他前置条件。

例如：

```text
角色 A：Dialogue → 好感度达标 → 专属事件 → 角色卡
角色 B：遭遇 → Battle 胜利 → Dialogue 认可 → 角色卡
角色 C：委托事件 → 好感度变化 → Dialogue 选择 → 角色卡
角色 D：首次 Battle 失败 → 再次相遇 → Event → 再战 → 角色卡
```

**收服本身就是角色 RPG 内容的一部分。**

### 契约、已管理角色卡与随身角色卡是不同层次

角色卡进入玩家体系以后，需要区分三种不同事实：

```text
Contract / 契约关系
= 玩家与该角色的正式关系已经成立

Managed Card / 已管理角色卡
= 代表该角色的卡已经进入玩家在中心管理器中的角色卡集合

Carried Card / 随身角色卡
= 这次旅行中实际被主公带在身上的角色卡
```

把一张卡从随身位移回中心管理器，不会解除契约，也不会取消收服。它只表示：

> **这次旅行没有把这名从者带在口袋里。**

因此“已收服多少角色”与“当前能带多少角色”是两个独立概念。

### 收服后关系继续发展

获得角色卡只是关系阶段变化：

```text
未收服
  ↓
建立关系 / 完成条件
  ↓
角色卡进入中心管理体系
  ↓
编入随身位
  ↓
Pocket Dialogue / Event / Battle
  ↓
训练 + 关系深化 + 战术协作
  ↓
角色剧情、能力与角色卡继续成长
```

因此好感度在收服后仍然有意义。

## 角色本体、契约与不同显现

### 角色本体不会因为收服而消失

一个角色被收服后，**角色本体仍然继续存在于 Map 世界中**。

同一个角色可以同时是：

- 功能性 NPC；
- 剧情人物；
- 好感度 / 关系对象；
- 可收服从者；
- 口袋陪伴角色；
- Battle 单位；
- 其他角色关系中的主公。

例如一个商店老板被收服后仍然可以继续经营商店，并继续参与自己的剧情和 Dialogue。

这意味着：

> **从者首先是持续存在于世界中的人物；收服使主公获得与其持续连接、随身同行和调用其力量的正式关系。**

### 契约是关系，不是物理占有

当前设计中，“契约”是工作概念，用于表达人与人之间成立的正式关系。

角色卡不是装着角色本人的容器，也不以写实的复制 / 克隆解释 Battle 或口袋里的角色。

角色卡是：

- 身份凭证；
- 关系证明；
- 持续连接媒介；
- 口袋陪伴媒介；
- Battle 力量调用媒介；
- 后续编队与成长的持卡者侧载体。

“契约”以及相关力量的正式世界观名称、来源和制度暂不锁定。

### 同一角色的三个表现层次

当前使用三个工作概念描述同一个角色的不同表现：

1. **世界本体（World Character）**
   - 真正存在于 Map 世界中的人物；
   - 保留职业、位置、NPC 功能、剧情与社会关系；
   - 可以面对面 Dialogue 和 Event。

2. **口袋化身（Pocket Manifestation，工作术语）**
   - 通过随身角色卡与持卡者持续同行时的轻量显现；
   - 可以 Dialogue、回应选择、评论地点 / NPC / 事件；
   - 可以参与随行和角色事件。

3. **战斗化身（Battle Manifestation，工作术语）**
   - 通过随身角色卡在 Battle 中完整显现的战斗形态；
   - 承载角色的战斗能力和 Battle 表现。

```text
                 同一个角色
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
      世界本体    口袋化身    战斗化身
      Map/NPC     Companion     Battle
          │          │          │
          └──────────┼──────────┘
                     ▼
             同一关系 / 同一角色事实
```

三者不是三个独立人物：

- 好感度不是三份；
- 收服状态不是三份；
- 核心剧情不是三套；
- Pocket Dialogue 可以感知角色本体已经经历的事件；
- 世界本体也可以感知持卡者携带该角色经历过的旅途和 Battle。

剧情中如果角色本体就在现场，也允许直接以 **本体参战**。Battle 规则不需要因此建立另一套战斗系统。

## “口袋”与持续陪伴

“口袋从者”中的“口袋”表达的是核心玩家幻想：

> **主公能够把已经收服的从者带在身边，一起旅行、交流、经历事件并参加战斗。**

因此口袋不是单纯的 Battle 卡槽。

放入口袋的从者应该能够：

- 主动或被动进行 Pocket Dialogue；
- 评论当前地图与地点；
- 对 NPC、物品和事件产生反应；
- 参与随行 Event；
- 对 Battle 前后发生的事情作出回应；
- 根据角色关系产生不同内容。

所以“这次旅行带谁”同时是：

```text
Battle 编队
+ Dialogue 编队
+ 探索编队
+ 角色事件编队
```

### 随身角色卡数量有限

主公不能把所有已经获得的角色卡同时带在身上。

当前确认：

```text
序章随身角色卡上限 = 1
当前随身角色卡 = 宿敌卡
```

后续随身角色卡位随着剧情推进逐步解锁。具体最终上限和每次解锁数量暂不确定，但“携带能力随着冒险推进成长”本身属于正式设计。

这意味着随身队伍选择具有真实成本：携带某个角色，不只是选择一个 Battle 单位，也同时决定本次旅途中能够出现哪些 Pocket Dialogue、环境反应、角色 Event 和探索内容。

原则上只有 **当前随身角色卡** 才进入本次旅行的 Pocket / Battle 编队：

```text
随身角色卡
→ Pocket Dialogue
→ 环境 / NPC / Event 反应
→ 当前 Battle 可调用角色

中心管理器中的其他角色卡
→ 契约继续存在
→ 关系继续存在
→ 不作为当前 Pocket Companion
→ 不直接作为当前野外 Battle 调用对象
```

如果未来剧情需要特殊远程调用或例外机制，应作为明确剧情能力设计，而不是让未携带角色默认都能随时参与。

### 中心管理器负责全量角色卡管理

未编入随身位的角色卡统一保存在 **中心管理器** 中。中心管理器是工作概念，正式世界观名称和具体设施形态后续再定。

中心管理器承担类似传统 Pokémon PC / Box 的队伍整理位置，但服务于角色卡世界规则：

- 查看全部已经建立契约并进入管理体系的角色卡；
- 查看角色卡完整属性、能力、技能、训练状态、关系与其他详细资料；
- 将角色卡编入或移出随身位；
- 管理当前旅行队伍；
- 后续如有需要，可继续承载训练管理、契约记录等相关功能。

PokeMan **不提供类似 Pokédex 的随身全角色图鉴 / 全属性数据库功能**。玩家在旅途中不应通过一个万能菜单随时核实所有角色卡的完整属性。

需要查看和核实完整角色卡资料时，玩家回到中心使用管理器：

```text
旅行 / 探索
↓
回到中心
↓
查看全部角色卡与完整属性
↓
调整随身队伍
↓
重新出发
```

旅途中可以根据实际 gameplay 需要显示当前随身角色的必要即时信息，但“全量角色卡 + 完整属性核实”属于中心管理器职责。

## Battle 的产品定位

Battle 是 PokeMan 区别于传统 Pokémon 战斗体验的核心系统之一。

### 从者不是被逐步遥控的棋子

玩家的身份是主公，而不是直接接管从者身体的操作者。Battle 中，从者应当依据自身能力、性格、经验、关系和当前战局形成行动判断。

产品上的目标不是让玩家直接提交：

```text
向左移动两格
→ 使用技能 A
→ 指定敌人 B
```

而是让主公逐渐拥有向从者表达更高层战术意图的能力，例如：

```text
“先拉开距离，找机会反击。”
“别管防守，尽快解决对方。”
“保护自己，不要冒险。”
“把对方逼到墙边。”
“尽量不要下重手。”
```

从者根据这些意图和自身判断决定具体行动。

### LLM Decision 是战斗特色的一部分

Battle 当前的基本结构保持：

```text
Battle Observation / Constraints
          ↓
Decision / LLM
          ↓
PlanSubmission
          ↓
Simulation validation / execution
          ↓
Battle Result
```

未来加入主公战术系统以后，结构扩展为：

```text
主公战术指令 / Guidance
          ↓
从者能力 + 性格 + 战斗经验 + 好感 / 信赖 + 当前战局
          ↓
Decision / LLM
          ↓
PlanSubmission
          ↓
Simulation
          ↓
实际战斗结果
```

主公战术指令只是 Decision 的输入之一。它不绕过 Decision 直接生成 authoritative Battle action，也不越过 Simulation 修改位置、伤害、HP 或结果。

因此仍然保持：

> **Decision 决定想做什么；Simulation 决定能不能做、什么时候发生以及结果是什么。**

### 角色性格应该真实影响战斗

同一句战术意图，不同从者可以产生不同理解和执行方式。

例如主公说：

> “谨慎一点。”

可能出现：

```text
剑士：后撤一步，等待反击窗口
刺客：脱离正面位置，重新寻找机会
谨慎角色：优先保存自身状态
冲动角色：仍倾向主动进攻，但在高信赖下愿意收敛攻势
```

这种差异应成为角色内容的一部分，而不是所有从者最终都表现成同一个通用 AI。

## 养成方向

养成不应变成一个与世界角色脱节的“卡牌复制体等级”。

当前核心方向是：

> **玩家养成的是从者本身的能力，以及主公与从者之间越来越成熟的关系与战术默契。**

长期成长可以围绕：

- **角色关系成长**：Dialogue、Event、共同经历和选择；
- **契约 / 角色卡成长**：关系深化后解锁更完整的角色能力与连接；
- **Battle 训练与能力成长**：训练和实际参战提升从者可以做到的事情；
- **随行成长**：携带角色旅行、触发 Pocket Dialogue 和专属事件；
- **主公成长**：提升组织、携带、调用和向从者表达战术意图的能力；
- **战术默契成长**：随着关系深化，从者更愿意理解、采纳和执行主公的战术指令。

### 训练提升“从者能做到什么”

训练主要作用于能力侧，而不是关系侧。

可以逐步影响：

- 战斗基础能力；
- HP / 生存能力；
- 技能；
- 技能熟练；
- 移动与行动能力；
- 战斗知识；
- 能够理解和执行的复杂战术空间。

其核心语义是：

> **训练提高从者的能力上限。**

即使从者完全理解主公的命令，如果能力、技能或经验不足，也可能无法完成。

### 好感度提升“从者愿意多大程度遵循主公指令”

好感度 / 信赖不应只被转换成简单攻击力加成。

一个重要长期目标是：**关系越深，从者越愿意把主公的战术意图纳入自己的 Decision。**

概念上可以理解为：

```text
最终战斗判断
=
当前战局
+ 从者性格
+ 从者能力
+ 战斗经验
+ 自身判断
+ 主公 Guidance × 关系影响
```

这里不要求最终实现为简单数值权重；它首先描述产品语义。

例如同一句：

> “别冲上去，等她露出破绽。”

低关系阶段的从者可能更依赖自己的判断，甚至直接拒绝或弱化这条指令；关系深化后，则可能更愿意信任主公并认真执行。

因此成长不是单纯：

```text
Level 10 → Level 20
```

而是同时存在：

```text
从者越来越强
+
主公与从者越来越默契
```

这两条成长线最终在 Battle 中汇合。

### Battle Guidance 属于后续核心系统

未来的玩家战斗交互重点不是 direct-control，而是 **战术指令 / Player Guidance**。

其产品职责是：

- 允许主公表达高层战术意图；
- 把玩家意图作为 Decision context 的一部分；
- 让角色性格、训练程度和关系状态影响实际执行；
- 保持从者拥有自己的判断；
- 保持 Simulation 是最终 Battle gameplay authority。

完整的 Guidance UX、指令表达方式、关系影响规则、训练数值和从者拒绝 / 偏离指令的表现方式，后续结合正式养成阶段设计。

具体 Level、属性、技能、突破、契约阶段等数值规则仍未定型，不应为了 MVP 序章先建立一套通用养成框架。

## 遭遇、挑战与敌对战斗

Battle 不只是从 Map 打开的独立玩法，也是角色之间的一种 RPG 交互行为。

进入 Battle 前需要理解：

- 双方当前关系；
- 谁发起战斗；
- 另一方是否同意；
- 为什么战斗；
- Battle 之后关系如何改变。

### Visible Encounter 是长期基础玩法

PokeMan 的道路与危险区域长期以 **Visible Encounter（可见遭遇）** 作为基础遭遇形式。

核心原则是：

> **战斗对象首先作为 Map 世界里可以被玩家看见的人存在，然后才因为空间接触、发现、主动交互或剧情冲突进入 Dialogue / Challenge / Hostile Battle。**

基础流程为：

```text
Map 上出现角色 / Encounter Entity
↓
玩家能够提前看见对方
↓
双方发生空间关系
├─ 玩家主动靠近 / 交互
├─ 玩家进入对方视野或警戒范围
├─ 双方发生接触
└─ 剧情改变对方状态或位置
↓
Dialogue / Hostile Action / Challenge / Event
↓
必要时进入 Battle
↓
返回同一个世界
```

因此长期基础体验不是“走若干步后无预兆抽出一个隐藏敌人并直接切 Battle”。道路设计本身应该让玩家能够观察、预判和选择如何接近人物与冲突。

可见 Encounter 可以表现为：

- 混混、盗贼、敌对组织成员在道路上拦路或警戒；
- 独立修行者停留在某个地点，玩家可以主动接近交流或绕过；
- 其他主公在道路、城镇入口或训练地点活动，并可能发起 Challenge；
- 剧情条件满足后，某个角色被放置或移动到 Map 中形成新的 Encounter。

Scripted Encounter 仍然存在，但也应尽量通过“角色真的出现在 Map 中”表达，而不是在没有世界表现的情况下突然弹出 Battle。

### 可见 Encounter Entity 不一定都是长期角色

所有 Battle 对手都属于世界中的人物，但不意味着每个路边敌人都需要拥有永久 Character identity 和完整关系状态。

可以区分：

```text
Visible Encounter Entity
├─ ordinary / transient
│    → 本次或本区域使用
│    → 可以拥有本次 Dialogue / Battle identity
│    → 结束后最多记录 defeated / resolved / area state
│
└─ persistent character
     → stable characterId
     → affinity / hostile
     → contract / card relationship
     → story progress
     → 可以反复相遇、发展关系甚至收服
```

例如普通混混、一般帮派成员或普通挑战者可以只是区域级 Encounter Entity；宿敌、独立从者、重要主公、功能 NPC 和剧情人物则更适合作为 persistent character。

这保持了“所有人都真实存在于世界中”的体验，同时避免要求每个一次性路人都进入完整长期关系系统。

### 可见遭遇的空间触发

Visible Encounter 可以由地图上的空间关系触发，而不要求统一使用某一种规则：

```text
玩家主动交互
玩家进入 NPC 视野
玩家进入 proximity / contact range
NPC 已经处于拦路位置
剧情状态改变角色行为
```

MVP 不要求普通 NPC 已经具备复杂自主巡逻或追逐移动；例如混混可以先固定站在道路上，在玩家进入其发现范围后直接转入 Dialogue / Hostile Encounter。

长期如果真实剧情需要“NPC 发现玩家后主动走近、追逐或堵路”，再推动 Map 支持更完整的 NPC authoritative movement，而不是为 MVP 提前建立通用 NPC AI 系统。

### Battle 对手不等于从者

道路、地图事件和剧情中可以存在至少三类常见战斗对象。

#### 1. 敌对普通人物

例如：

- 打劫的混混；
- 太妹；
- 盗贼；
- 路霸；
- 敌对组织成员。

他们是普通世界人物，不要求拥有角色卡，也不要求可被收服。当其本人发动敌对行为时，可以由世界本体直接参加 Battle；玩家使用自己的随身从者应战。

战斗结果通常解释为击退、制服、认输或逃跑，而不是默认死亡。

#### 2. 独立从者 / 修行者

这些角色自身具有从者级战斗能力，但当前没有与玩家建立契约。

他们可以用本体直接参战。对战可能只是切磋，也可能成为未来关系和收服流程的一部分。

#### 3. 其他主公

其他主公可以使用自己持有的角色卡，让自己的随身从者参与 Battle，从而形成主公与主公之间的队伍对战。

Battle 前后仍然存在 Dialogue、关系变化与剧情状态变化。

因此 Battle actor 可以来自：

```text
普通人物本体
从者本体
随身角色卡调用的战斗化身
```

Battle actor 不应与 Character Card 绑定为同一个概念。

### 敌对行为触发强制 Battle

当一方已经处于明确敌对行为中，例如抢劫、袭击、堵路、追杀或剧情冲突，则可以直接进入强制 Battle：

```text
Visible Encounter
↓
敌对行为
↓
强制 Battle
↓
Battle Result
↓
Map / Dialogue / World State
```

玩家不需要先“同意接受挑战”，因为冲突已经成立。

### 非敌对角色通过邀请进入 Battle

如果双方当前并非敌对关系，正常 Battle 首先表现为挑战 / 邀请。

NPC 可以邀请玩家：

```text
角色邀请对战
↓
玩家选择
├─ 应战 → Battle
└─ 拒绝 → 返回 Map / Dialogue
```

玩家也可以主动邀请角色：

```text
玩家邀请对战
↓
角色根据关系 / 性格 / 当前状态 / 剧情条件判断
├─ 接受 → Battle
├─ 拒绝 → 返回 Map / Dialogue
└─ 提出条件 → Event / Dialogue
```

是否愿意切磋本身就是角色表达的一部分。

### 玩家可以强制开战

对于当前非敌对的角色，玩家可以越过对方意愿强制发动 Battle，但这不是普通挑战的快捷方式，而是明确的 RPG 行为。

例如：

```text
玩家邀请 Battle
↓
对方拒绝
↓
玩家选择强制开战
↓
关系恶化 / hostile 或警戒状态变化
↓
Battle
```

世界不默认玩家永远代表正确的一方。角色应该能够记住玩家的强制行为。

是否允许攻击某些特殊角色，可以继续受剧情保护、地图规则和角色状态限制。

### Battle 会影响关系

Battle 不采用统一的“胜利 = 好感 +N”。

关系结果至少可以考虑：

- 谁发起；
- 是否双方同意；
- 战斗原因；
- 胜负；
- 角色性格与价值观；
- Battle 前后 Dialogue / Event。

例如：

| 情境 | 可能结果 |
| --- | --- |
| 对方主动挑战，玩家接受并获胜 | 对方可能更加认可玩家 |
| 玩家邀请，对方接受切磋 | 好感 / 关系可能上升 |
| 玩家帮助角色击退敌人 | 好感可能上升 |
| 对方拒绝后玩家强制攻击 | 好感明显下降，并可能敌对 |
| 好战角色被玩家正面击败 | 可能增加认可 |
| 自尊心强的角色落败 | 可能暂时降低好感或触发新事件 |

“敌对”是动态关系 / 情境状态，而不是永久角色类别。一个敌人未来可以关系缓和，甚至最终成为从者；一个中立角色也可以因为玩家行为变成敌人。

MVP 阶段关系模型可以先保持最小：

```text
relation / affinity
+
hostile
```

只有真实内容需要时，再扩展“喜欢 / 尊敬 / 畏惧 / 敌意”等多维关系。

## 核心设计目标

1. **建立“主公与从者”的核心幻想**：角色先作为世界人物被认识，再成为可收服、随身陪伴和使用的伙伴。
2. **让角色卡表达真实的人际契约**：主公 / 从者是关系位置，双向契约真实成立，而不是序章教学特例。
3. **让“口袋”产生真实陪伴感**：玩家携带的不是纯战斗数据，而是一群会持续回应世界的角色。
4. **让随身卡位成为真实旅行选择**：已收服角色可以很多，但主公只能携带有限角色卡；带谁出门同时决定 Battle、Dialogue、探索与角色事件内容。
5. **让中心承担完整角色管理**：全部角色卡与完整属性在中心管理器中核实和整理，而不是通过随身全角色图鉴随时查询。
6. **保持地图 RPG 为核心体验**：地图承担旅行、地点、角色、事件、遭遇和世界展开。
7. **让可见遭遇成为道路基础玩法**：玩家先在 Map 中看到人物，再由空间接触、Dialogue、Challenge 或敌对行为自然进入 Battle。
8. **让 Dialogue 成为关系与陪伴的主要玩法**：关系必须通过具体交流与事件被玩家感知。
9. **让 Battle 成为自主角色战斗与主公战术协作的核心玩法**：从者拥有自己的 Decision，主公通过关系和战术意图逐步影响其判断。
10. **让 Battle 参与角色和世界推进**：Battle 由真实情境产生，并把结果带回世界。
11. **让收集建立在人物内容上**：高质量角色可以同时承担 NPC、剧情、陪伴和 Battle 职责。
12. **让养成同时包含能力与默契**：训练提高从者能力，好感 / 信赖提高战术协作和指令遵循程度。
13. **延续 `essentials-v21.1` 的 GBA 视觉基础，但保持用户本地构建边界**：先在已有地图与素材上建立产品循环，同时不把原版素材作为 PokeMan 自身分发内容。
14. **保留完整 RPG 成长空间**：主公、从者、关系、角色卡、探索、事件、战斗和世界状态可以逐步扩展。

## 第一阶段体验目标

PokeMan 的第一个 playable slice 应证明一个真正有产品意义的连续体验，而不是分别证明 Map、Dialogue、Battle 能运行。

玩家至少需要亲手经历：

```text
Map
→ World Dialogue
→ 双向 Character Card
→ 宿敌卡自动占用唯一随身位
→ LLM-driven Battle
→ 再次面对角色本体
→ Pocket Companion
→ Pocket Dialogue
→ Visible Encounter
→ 强制 / 可选 Battle
→ Pocket Dialogue
→ 到达新的城镇
→ 发现未来可以继续认识和收服的人物
```

序章只需要让玩家理解“角色卡关系可以真实双向成立”“随身携带决定当前同行从者”以及“从者会通过角色卡自主参战”这几件事，不要求此时已经开放完整 Player Guidance、训练或关系影响 Decision 的机制。

这同时会真实验证 Map、Dialogue、Battle、Realm State、Frame / Runtime 控制流和多个 `game-libs` 的组合能力。

# MVP 序章

## 序章目标

MVP 序章应该像 GBA 时代宝可梦、尤其类似《红宝石 / 蓝宝石》开局那样，从一个非常小而安全的起点开始，然后通过道路第一次把玩家送进更大的世界。

但产品语义改造成口袋从者自己的结构。

序章的首要目标是 **建立世界观和核心产品认知**，不是展示完整养成系统。

序章结束时，第一次接触游戏的玩家应该已经理解：

- 自己在主要冒险关系中是主公，但主公 / 从者是关系位置，不是永久身份；
- 世界中的人物可以与自己建立角色卡关系；
- 双向角色卡契约可以真实成立；
- 自己本人也可以被角色卡代表，并通过战斗化身参与 Battle；
- 角色卡不会让人物本体消失；
- 已收服的角色卡与当前随身携带的角色卡不是同一个概念；
- 序章阶段主公只能携带一张角色卡，宿敌卡占用这个唯一随身位；
- 未随身携带的角色卡进入中心管理体系，契约本身不会因此解除；
- 角色卡可以让当前随身从者进入口袋持续陪伴；
- 角色卡可以在 Battle 中调用当前随身从者力量；
- Battle 中的从者具有自己的行动判断，而不是等待主公逐步遥控；
- 道路上的 Encounter 以可见人物为基础，玩家能够在进入互动前先看见对方；
- 道路上存在敌对遭遇、可选挑战和其他角色；
- 离开出生地之后，还有城镇、人物和新的收服可能性等待探索。

序章不要求玩家此时理解或掌握完整的训练、好感度影响战术执行、Player Guidance 或高级养成规则，也不要求立刻决定玩家自己的角色卡在序章之后是否可以继续向更多人分发。

## MVP 空间边界

序章当前明确覆盖三段空间：

```text
【出生镇】
主角家
→ 小镇
→ 博士研究所
→ 与宿敌建立双向角色卡
→ 宿敌卡进入唯一随身位
→ 教学 Battle

        ↓ 离开安全区

【第一条道路】
第一次 Pocket Dialogue
→ 环境反馈
→ 看见道路上的敌对人物
→ 第一次敌对遭遇 / 强制 Battle
→ Battle 后 Pocket Dialogue
→ 看见独立从者 / 修行者
→ 主动接近或被邀请
→ 可选 Challenge

        ↓ 完成第一次旅行

【第一个城镇】
进入真正的城镇空间
→ 普通居民与功能 NPC
→ 完成博士交代的外出目标
→ 发现新的重要人物 / 潜在从者
→ Pocket Dialogue
→ 序章结束
```

**MVP 边界停在第一个城镇。**

当前不继续扩展到第二条道路、完整任务系统、完整城镇循环、道馆式结构或第二个正式收服角色。第一个城镇需要让玩家看到“世界接下来还会继续展开”，但不需要把所有长期系统一次做完。

## 第一阶段：出生镇——身份与系统教学

出生镇是安全、熟悉且很小的起点，主要承担玩家身份和基础系统教学。

这里原则上不安排随机敌对遭遇，让玩家先理解世界和基本操作。

### 第一幕：家中醒来

```text
标题 / 开场
↓
主角家中醒来
↓
获得移动控制
↓
少量家人 / 物件互动
↓
得知博士正在找自己
↓
离开家
```

最低目标：

- 四方向 Map 移动成立；
- 室内外切换成立；
- 基础 World Dialogue 成立；
- 玩家自然获得“去研究所”的目标。

这里不解释角色卡和 Battle。

### 第二幕：第一次探索出生镇

玩家离开家后可以在出生镇短暂自由探索，而不是直接传送到博士面前。

最低目标：

- 少量 NPC 可 Dialogue；
- 路牌 / 建筑可以交互；
- NPC 可以提前提到博士正在研究角色卡；
- 有人提到宿敌也被博士叫去了；
- 玩家自行找到并进入研究所。

这一段只制造兴趣，不完整讲规则。

### 第三幕：博士与宿敌登场

宿敌已经在研究所。

```text
玩家进入
↓
博士欢迎
↓
宿敌插话
↓
建立两人的熟识 / 竞争关系
↓
博士说明今天叫两人来的原因
```

博士首先承担 **角色卡体系研究者 / 引导者** 的剧情功能。

序章理论说明只需要让玩家知道：

- 人与人之间可以建立正式连接；
- 成立以后可以形成对应角色卡；
- 持卡者能够与角色持续保持联系；
- 在需要时能够调用对方的力量；
- 这种关系可以双向成立。

角色卡历史、力量来源和社会制度暂不解释。

### 第四幕：主角与宿敌建立真实双向契约

博士指导双方建立第一次双向连接：

```text
玩家获得：宿敌角色卡
宿敌获得：主角角色卡
```

“互换”不是交换唯一实体，而是双方都获得代表对方的角色卡。

**这里的两张角色卡都是真实契约结果，不是临时教学卡。**

这一幕正式建立：

> **主公 / 从者是一种关系位置，而不是把人类永久划分成两个固定身份。**

因此：

```text
玩家相对宿敌：持有宿敌卡，是宿敌的主公
宿敌相对玩家：持有玩家卡，是玩家的主公
```

双方同时又是对方的从者；这不影响两人各自继续建立其他主公 / 从者关系。

序章之后，宿敌是否长期保留玩家卡，以及玩家是否能够继续向其他角色分发自己的卡，属于后续剧情和长期系统设计，不影响本次双向契约本身真实成立。

### 第五幕：第一次角色卡反馈

玩家应该得到明确的“获得宿敌”反馈。

序章阶段玩家的随身角色卡上限为 1，因此宿敌卡获得后直接进入唯一随身位。

MVP 不需要完整中心管理器或队伍管理 UI，但至少需要：

- 显示宿敌身份；
- 显示角色卡已经获得；
- 表达宿敌卡已进入唯一随身位 / 可用状态；
- 为后续 Battle 和 Pocket Dialogue 建立预期；
- 通过剧情或 UI 同时确认宿敌也真实持有玩家角色卡。

完整的全量角色卡查看、属性核实和随身队伍调整留到以后中心管理器真正需要时实现。

### 第六幕：第一次 Battle——交换彼此的力量

研究所立即进行一次测试 Battle：

```text
现实：
玩家本人                    宿敌本人
   │                           │
随身携带宿敌卡             持有主角卡
   │                           │
   ▼                           ▼

Battle：
宿敌战斗化身      VS      主角战斗化身
     │                       │
     └────── Decision / LLM ─┘
              ↓
          Simulation
```

这一战主要证明：

- 双向契约已经真实成立；
- 人物本体仍在现实世界；
- 代表双方的角色卡同时存在；
- 玩家本人也属于可以被角色卡代表和调用战斗化身的角色；
- 玩家当前随身卡决定本次可以调用的从者；
- Battle 中可以显现同一人物的战斗力量；
- 角色卡不是把人物本人装进去；
- 战斗化身拥有自己的行动判断，不需要玩家逐格直接控制。

第一次 Battle 只需要最小闭环：

```text
进入 Battle
→ 显现
→ Decision 产生行动
→ 移动 / 攻击 / 技能
→ Simulation 决定结果
→ 胜负
→ 返回研究所
```

Battle 使用 `@loomrealm-game/battle` 当前已有的 Decision / Simulation / Presentation 模型，不为了模仿 Pokémon 改造成传统宝可梦菜单战，也不为了序章先补 direct-control 模式。

完整的 Player Guidance / 战术指令系统属于后续养成阶段；序章只建立“角色会通过角色卡自主战斗”的认知。

### 第七幕：Battle 后再次面对本体

回到研究所后，宿敌本人仍站在原地，玩家本人也一直没有因为自己的战斗化身被调用而从现实中消失。

通过非常短的 Dialogue 强化“Battle Manifestation ≠ 本体消失”。宿敌也可以评论自己的战斗表现、玩家战斗化身或 Battle 结果，让规则通过人物性格自然呈现。

### 第八幕：博士给予第一次外出任务

博士给玩家一个规模很小、目的地位于**第一个城镇**的任务。

任务可以是：

- 把某样东西送给第一城镇的人；
- 去找一个博士认识的人；
- 调查第一道路或城镇附近的某件事；
- 到第一城镇确认某项信息。

具体内容后续再定。

关键条件是：

> **宿敌本体暂时留在研究所，而玩家带着唯一随身角色卡——宿敌卡——独自出发。**

这建立了第一次真正的空间分离。

如果序章继续保留宿敌手中的玩家角色卡，也可以在后续剧情中进一步证明：一张角色卡不仅让持卡者调用战斗力量，也可能成为双方跨空间 Dialogue、陪伴和信息共享的关系媒介；但 MVP 不要求立即实现这一整套双向远程玩法。

## 第二阶段：第一条道路——第一次真正旅行

第一条道路是序章真正从“系统教学”转向“RPG 冒险”的位置。

这里应第一次让玩家体验：

```text
安全区
→ 旅行
→ Pocket Companion
→ Visible Encounter
→ Battle
→ Relationship
→ 新人物
```

### 第九幕：第一次 Pocket Dialogue

玩家离开出生镇不久，宿敌第一次通过当前随身角色卡主动说话。

此时玩家明确知道：

- 宿敌本体留在博士研究所；
- 自己已经离开出生镇；
- 宿敌卡是自己当前唯一随身角色卡；
- 但宿敌仍然可以和自己交流。

这一幕第一次真正解释“口袋从者”：

> **角色不是只有 Battle 开始时才有意义，而是真的被主公带在身边旅行。**

### 第十幕：第一次环境反应

随后至少安排一个由宿敌主动感知道路环境的反馈，例如：

- 评论镇口；
- 提醒前方危险；
- 评价某个路人；
- 评论某个地点 / 路牌 / 物件。

这证明 Pocket Companion 不是远程通讯录，而是在共同经历当前世界。

### 第十一幕：第一次可见敌对遭遇——强制 Battle

第一道路安排一个玩家能够提前看到的敌对普通人物，例如混混、太妹、路霸或抢劫者。

```text
玩家在道路上先看到敌对人物
↓
继续接近 / 进入对方发现范围
↓
敌对人物拦住玩家
↓
Dialogue / 威胁 / 抢劫
↓
hostile 已成立
↓
强制 Battle
↓
玩家通过唯一随身角色卡调用宿敌战斗化身
↓
宿敌由 Battle Decision 自主应战
↓
击退对方
↓
返回 Map
```

这场 Battle 与研究所教学战语义不同：

- 研究所战是在测试角色卡；
- 这一战是玩家在真正旅行中看见并进入一场现实冲突，需要从者帮助自己解决问题。

战斗结束后立即发生 Pocket Dialogue，让宿敌对结果产生反应。

MVP 不要求混混已经会在地图上复杂巡逻或追逐。只要玩家能提前看见对方，并在进入其空间触发条件后自然进入冲突即可。

### 第十二幕：第一次可见的可选 Challenge

同一条道路上再放置一个玩家能够提前看见、也可以选择绕过的非敌对独立从者 / 修行者。

玩家主动接近并发生 World Dialogue，或者对方在合适的范围内主动提出切磋：

```text
玩家看见修行者
↓
可以绕过
或
主动接近 / 被邀请
↓
World Dialogue
↓
对方邀请 Battle
↓
[应战]
[拒绝]
```

MVP 应尽可能允许“绕过”和“拒绝”真正成立，以证明 Battle 不是所有角色交互的强制终点。

如果玩家接受，则使用同一个 Battle 系统进入一场双方同意的 Challenge；如果玩家拒绝，则关系和世界流程正常继续。

这一人物可以成为序章之后未来能够继续认识、挑战甚至收服的 persistent character，但 MVP 不要求在这里完成其收服。

这一幕同时让玩家第一次理解：

```text
地图上看见敌对人物
→ 接近后可能被强制卷入 Battle

地图上看见非敌对人物
→ 可以绕过、交谈、接受或拒绝 Challenge
```

玩家主动邀请别人或强制发动 Battle 的完整操作入口可以在 MVP 或后续迭代继续补全，但底层语义从序章开始保持一致。

## 第三阶段：第一个城镇——世界正式展开

第一个城镇是 MVP 序章的真正终点。

进入城镇时，玩家应该第一次产生：

> **“我已经离开家，进入更大的世界了。”**

它不是第二个出生镇，而是第一次展示正式 RPG 社会空间。

### 第十三幕：进入第一个城镇

最低应该能够看到：

- 城镇入口与明确空间边界；
- 普通居民；
- 至少一个功能 NPC / 功能地点；
- 至少一个值得继续认识的重要人物；
- 通向未来地区的出口或视觉提示。

功能设施不要求一次全部实现。重点是让玩家看到世界比出生镇更大、更复杂。

### 第十四幕：功能 NPC 也是角色

第一个城镇应该第一次明确展示：

> **“NPC”不是一种不能成为从者的角色类别。**

可以安排一个商店老板、治疗人员、旅店角色、守卫、研究者或其他功能角色。

当前玩家只需要和其完成正常 World Dialogue / 功能交互，但可以通过 Dialogue、宿敌评论或事件暗示此人同样具有自己的能力、关系和故事，未来甚至可能成为从者。

这样直接证明已有设计原则：

```text
功能 NPC
+ 剧情人物
+ 关系角色
+ 可收服从者
```

可以是同一个人。

### 第十五幕：完成博士的第一次外出目标

玩家在第一个城镇完成博士交代的简单任务。

任务完成不需要演变成完整 Quest System；MVP 只需要一个明确的世界状态变化：

```text
博士任务未完成
↓
到达城镇 / 找到人物 / 交付物品 / 获得信息
↓
任务目标完成
```

这个过程用于证明：

- 从一个 Map 出发；
- 穿过另一张道路 Map；
- 看见并经历 Encounter 和 Battle；
- 到达新的城镇；
- 世界状态可以持续保存并推进。

### 第十六幕：新的潜在从者与序章结束

第一个城镇里至少出现一个值得玩家继续认识的重要人物。

玩家不必马上收服这个人，只需要发生：

- 一次有角色感的 World Dialogue；
- 一次选择或初始关系变化；
- 一条未来可以继续发展的角色线索；
- 宿敌的一次 Pocket Dialogue 反应。

这会把玩家刚刚学会的规则投射到整个城市和未来世界：

> **这些生活在世界中的人，都可能拥有自己的故事、关系、战斗能力和收服路径。**

随后序章结束，把自由探索和下一阶段目标交给玩家。

## 序章的三层验证循环

扩展到第一个城镇之后，MVP 不只验证角色卡，还要同时验证三层循环。

### 1. 角色循环

```text
认识角色
→ 建立角色卡关系
→ 进入中心管理体系
→ 编入有限随身位
→ Pocket Dialogue
→ Battle
→ 继续关系
```

### 2. 遭遇循环

```text
Map
→ 看见 Encounter Entity / Character
→ 接近、发现或主动交互
→ Dialogue / Hostile Action / Challenge
→ Battle、拒绝或绕过
→ Relationship / World State
→ Map
```

### 3. 旅行循环

```text
中心整理随身角色卡
→ 安全区
→ 道路
→ 可见遭遇
→ 新城镇
→ 新人物和未来目标
→ 回到中心重新整理
```

只要这三层都成立，PokeMan 就已经具备真正的 GBA 风格角色收集 RPG 骨架，而不是单纯的技术 vertical slice。

## MVP 明确不要求完成

序章阶段暂不要求：

- 第二条道路；
- 第二个完整城镇；
- 正式完成第二个从者的收服；
- 完整任务 / Quest 框架；
- 完整商店、旅店、治疗等所有城镇系统；
- 完整中心管理器 UI 与多角色队伍调整；
- 序章之后随身角色卡位的具体解锁节奏与最终上限；
- 玩家自己的角色卡在序章之后向更多人分发的完整规则；
- 多人同时持有同一角色卡关系的权限和同步规则；
- 完整养成与属性体系；
- Battle Player Guidance / 战术指令系统；
- 训练对从者能力的长期成长；
- 好感度 / 信赖对从者遵循战术指令程度的完整规则；
- 复杂 NPC 巡逻、追逐和通用地图 AI；
- 多维复杂关系系统；
- 完整主线故事；
- 道馆式长期挑战结构。

这些能力只有在第一个城镇以前的产品闭环成立后再继续扩展。

## 设计原则

- **玩家在主要冒险视角中是主公，但主公 / 从者首先是关系位置，而不是固定物种、阶级或永久身份。**
- **序章的双向契约真实成立，不使用临时教学卡解释。**
- **玩家本人也属于可以被角色卡代表、持续连接并产生战斗化身的角色。**
- **从者先是世界人物，之后才同时成为某位主公的随行和战斗角色。**
- **契约、已管理角色卡和当前随身角色卡是不同层次；把卡放回中心不会解除契约。**
- **主公只能携带有限数量角色卡；序章上限为 1，后续随剧情解锁更多随身位。**
- **“口袋”意味着当前随身从者的持续陪伴，不只是 Battle 卡组。**
- **被放入口袋的从者能够 Dialogue，并参与探索和事件反馈。**
- **未随身携带的角色卡仍保留契约与关系，但默认不参与当前 Pocket Companion 和野外 Battle。**
- **中心管理器承担全部角色卡管理和完整属性核实，不提供随身全角色 Pokédex 式完整数据库。**
- **收服不会让角色本体从 Map 世界消失。**
- **功能 NPC、剧情角色和可收服从者可以是同一个人。**
- **世界本体、口袋化身和战斗化身属于同一个角色。**
- **三种表现共享核心关系和角色事实。**
- **角色卡表达正式关系的成立，不规定统一捕获动作。**
- **角色卡是契约、持续连接和力量调用媒介，不是装着人物的容器。**
- **道路与危险区域以 Visible Encounter 作为长期基础玩法，人物先存在于 Map，再进入互动或 Battle。**
- **普通 Encounter Entity 可以是短期 / 区域性人物，重要角色才需要完整长期 Character identity。**
- **Battle 是 PokeMan 区别于传统 Pokémon 的核心体验之一。**
- **从者在 Battle 中拥有自身 Decision，不把玩家设计成逐格遥控从者的操作者。**
- **LLM / Decision 负责形成战术意图和具体 Plan，Simulation 始终拥有 Battle gameplay authority。**
- **未来主公通过 Player Guidance / 战术指令影响 Decision，而不是绕过 Decision 直接控制 Simulation。**
- **训练主要提高从者“能做到什么”，好感 / 信赖主要提高主公战术意图对从者 Decision 的影响。**
- **角色性格、能力、经验、关系和当前战局都可以影响从者实际战斗判断。**
- **Battle 对手不等于从者。**
- **普通人物本体、独立从者本体和随身角色卡调用的战斗化身都可以成为 Battle actor。**
- **敌对行为可以强制触发 Battle。**
- **非敌对 Battle 通过邀请 / Challenge 与应战产生。**
- **玩家可以拒绝挑战，也可以主动挑战别人。**
- **玩家可以强制发动 Battle，但必须承担关系和世界状态后果。**
- **Battle 对关系的影响由情境决定，而不是统一胜负加减好感。**
- **敌对是动态关系状态，不是永久角色类别。**
- **好感度服务于真实人物关系，并在收服后继续影响陪伴、事件和未来战术协作。**
- **随身编队同时具有 Battle、Dialogue、探索和角色内容意义。**
- **地图探索是 RPG 世界体验基础。**
- **Dialogue 服务于人物、关系、陪伴、事件、选择和世界表达。**
- **不同从者允许拥有不同收服逻辑。**
- **PokeMan 自身不捆绑分发原版 Pokémon / Essentials 素材，用户在本地提供 `essentials-v21.1` 参与构建。**
- **MVP 序章只负责建立世界观和核心循环，不要求提前完成养成系统。**
- **MVP 先完成“出生镇 → 第一道路 → 第一个城镇”的完整旅行体验。**
- **先让真实玩法成立，再增加复杂系统。**
- **新增能力服务于真实游戏体验，不为了展示技术能力。**
- **通过 PokeMan 的真实需求检验 LoomRealm Core 与 `game-libs`，而不是围绕框架反向设计游戏。**

## 当前非目标

当前阶段不以以下内容作为目标：
