# 第一阶段 DOM 渲染与渲染状态

## 1. 文档目的

本文档记录 LoomRealm 第一阶段地图运行时原型的渲染方向，以及后端、FSDB、状态同步、资源访问和前端 DOM 渲染之间的职责边界。

第一阶段不使用 Canvas 或 WebGL，而是使用 DOM 与 CSS 将前端状态渲染为地图和人物画面。

具体组件框架、文件目录、CSS 命名、资源接口形式和实现代码由开发阶段决定。

## 2. 总体渲染链路

第一阶段采用以下链路：

```text
FSDB 静态项目定义
        ↓
后端读取、校验并转换
        ↓
后端权威状态
        ↓
客户端可见状态投影
        ↓
通用状态同步
        ↓
前端状态镜像
        +
图片资源缓存
        +
本地表现状态
        ↓
DOM 场景投影
        ↓
HTML 元素与 CSS
```

最核心的分工是：

> 后端负责把 FSDB 和游戏逻辑转换为可渲染状态；前端负责把可渲染状态与图片资源转换为 DOM 画面。

后端不发送 DOM 操作或绘制命令，例如：

```text
createElement
removeElement
setStyle
moveElement
drawTile
drawSprite
```

渲染方式属于前端实现细节，不属于运行时协议。

## 3. 后端职责

后端完整读取并理解项目 FSDB。

第一阶段后端负责：

- 读取地图定义；
- 读取地图瓦片布局；
- 读取并解析 Tileset 定义；
- 读取人物定义；
- 校验实体、引用、坐标、Tile 索引和资源引用；
- 处理用户动作；
- 处理人物移动与碰撞；
- 处理 Portal 与地图跳转；
- 持有地图和人物的权威逻辑状态；
- 从内部权威状态生成客户端可见状态；
- 向前端同步完整状态或状态变化；
- 提供状态中引用的图片资源访问能力。

后端内部状态不应直接完整序列化给前端。后端应输出一份稳定的客户端可见状态，使前端能够重建当前画面，同时不暴露与渲染无关的内部结构。

## 4. 前端不读取完整 FSDB

前端不需要完整读取、遍历或解析项目 FSDB。

前端不需要理解：

- `[struct]`、`[extend]`、`[group]` 和 `[resource]` 的数据库组织方式；
- `.info.meta`、`.extend.meta` 和其他 FSDB 元数据；
- FSDB 目录结构；
- 数据实体之间的原始引用解析规则；
- 项目完整性校验规则；
- 运行时内部领域模型。

前端只接收后端已经解析、校验和投影后的客户端可见状态。

这一边界保证：

- 本地 Worker 与远程服务端可以使用相同前端；
- FSDB 结构调整不会直接影响 DOM 渲染层；
- 前端不会与后端各自维护一套 FSDB 解释逻辑；
- 前端和后端不会因为读取到不同版本的项目数据而产生状态分歧。

## 5. 客户端可见状态

客户端可见状态是权威状态中面向渲染的一份投影。

第一阶段概念上至少包括：

```text
当前地图
├── 地图标识
├── 地图宽高
├── Tile 宽高
├── Tileset 渲染定义或引用
├── 地图瓦片布局
└── 地图内容版本

玩家
├── 人物定义或渲染定义
├── 人物图片资源引用
├── 逻辑位置
├── 朝向
└── 移动状态

运行状态
├── 正常运行
├── 地图切换中
└── 故障
```

这些内容足以让前端建立或更新当前 DOM 场景。

图片二进制不进入 JSON 状态。客户端可见状态只携带稳定的图片资源引用和必要的切片信息。

第一阶段在首次进入地图或完成地图跳转时，可以同步当前地图的完整可渲染状态；普通人物移动只同步人物动态状态变化。

## 6. 资源访问边界

前端通过资源接口获取状态中引用的实际图片文件，例如：

- `tile.sheet`；
- `actor.sprite`。

资源接口负责交付资源内容，不负责解释完整游戏状态。

图片资源本身不能告诉前端：

- 地图有多宽或多高；
- 每个地图位置使用哪个 Tile；
- Tile 的宽高和图集列数；
- 玩家当前位于哪里；
- 玩家朝向哪个方向；
- 人物 Sprite Sheet 如何切帧。

这些渲染信息必须来自客户端可见状态。

因此准确边界是：

> 前端通过状态同步获得已经解析好的地图和人物渲染数据，并通过资源接口加载这些数据所引用的图片。

前端可以缓存、释放或重新加载图片资源，但资源缓存不属于权威游戏状态。

## 7. 前端维护的三类数据

### 7.1 权威状态镜像

权威状态镜像是后端同步到前端的客户端可见状态副本，例如：

- 当前地图及其可渲染定义；
- 玩家逻辑位置；
- 玩家朝向；
- 玩家移动状态；
- 运行时状态版本；
- 地图切换和故障状态。

前端不能通过修改这份镜像改变游戏结果。

### 7.2 静态资源缓存

静态资源缓存保存已经加载的渲染资源和派生缓存，例如：

- `tile.sheet` 图片；
- `actor.sprite` 图片；
- Tileset 切片计算结果；
- 当前地图的瓦片 DOM 或样式缓存。

资源缓存可以随时重新构建，不是游戏权威状态。

### 7.3 本地表现状态

本地表现状态只影响画面，不影响游戏规则，例如：

- 人物在两个逻辑格之间的像素插值进度；
- 当前人物动画帧；
- 场景视觉偏移；
- 地图切换遮罩；
- 资源加载状态；
- 调试图层开关。

基本边界是：

```text
玩家位于哪个逻辑格
    = 后端权威状态

人物当前绘制在两个格子之间的哪个像素位置
    = 前端表现状态
```

## 8. DOM 场景投影

同步状态不直接等同于最终 DOM。

前端在状态镜像和 DOM 之间建立一层 DOM 场景投影：

```text
前端状态镜像
        +
图片资源缓存
        +
本地表现状态
        ↓
DOM 场景投影
        ↓
DOM 节点与 CSS 属性
```

DOM 场景投影负责决定：

- 显示哪张地图；
- 创建哪些瓦片元素；
- 每个瓦片使用图集中的哪个区域；
- 人物元素位于何处；
- 人物当前朝向；
- 是否显示行走动画；
- 是否显示调试层或地图切换遮罩。

DOM 不负责解释游戏规则，也不参与移动、碰撞和 Portal 判定。

## 9. DOM 场景结构

第一阶段的 DOM 场景可以划分为以下概念层：

```text
game viewport
└── game scene
    ├── tile layer
    ├── portal debug layer
    ├── actor layer
    └── overlay layer
```

各层职责：

- **game viewport**：固定显示区域并裁剪场景外内容；
- **game scene**：表示当前完整地图场景；
- **tile layer**：渲染地图瓦片；
- **portal debug layer**：仅在调试模式下显示 Portal 和碰撞区域；
- **actor layer**：渲染玩家及后续动态人物；
- **overlay layer**：显示地图切换遮罩、资源加载状态和故障信息。

具体标签和 CSS 类名不在本文档中固定。

## 10. 地图瓦片渲染

第一阶段采用一个地图格子对应一个 DOM 元素的方式。

后端同步给前端的可渲染地图数据已经由以下 FSDB 内容转换而来：

```text
map.tile
    地图坐标和 tileIndex

tile.set
    Tile 宽高、图集列数和资源引用

tile.sheet
    实际图集图片
```

前端不直接读取这些 FSDB 表，而是接收其对应的客户端可见状态。

每个瓦片元素使用图集图片作为背景，通过 `tileIndex` 与 Tileset 切片信息计算背景位置。

第一阶段优先使用 CSS Grid 表达完整矩形网格。若后续采用稀疏地图、多图层或任意位置对象，再评估绝对定位、视口裁剪或其他策略。

## 11. 人物 DOM 表达

人物在 DOM 中分为两个视觉职责：

```text
人物位置容器
    表示人物在地图中的逻辑占用位置

人物精灵元素
    表示实际可见的角色图片和动画帧
```

人物位置容器按照权威逻辑坐标定位。

人物精灵元素可以高于或宽于一个 Tile，并以人物脚下位置作为视觉锚点。视觉图片尺寸不改变人物逻辑占用范围。

前端从客户端可见状态获得：

- 人物图片资源引用；
- 单帧尺寸；
- 行列数量；
- 方向顺序；
- 人物逻辑位置和移动状态。

实际图片通过资源接口加载。

## 12. 人物移动与动画

当运行时确认玩家从一个逻辑位置移动到另一个逻辑位置后，前端根据新的权威位置更新人物 DOM 的目标位置。

第一阶段优先采用：

> 格子逻辑移动，DOM 使用 CSS Transform 进行像素级平滑表现。

CSS Transition、Web Animations API 或前端动画循环只负责视觉表现，不能作为游戏逻辑完成的判据。

运行时同步人物朝向和移动状态；实际显示哪个动画帧由前端决定。人物动画帧和插值进度属于本地表现状态。

正确的数据方向是：

```text
运行时权威位置
        ↓
前端状态镜像
        ↓
计算人物 DOM 目标位置
        ↓
CSS Transform 表现移动
```

前端不能通过读取 DOM 当前位置反推玩家逻辑位置。

## 13. 状态更新与 DOM 更新

前端不应在每次状态变化时重新创建整个地图 DOM。

### 首次加载或地图切换

重新构建：

- 地图瓦片 DOM；
- 地图尺寸和 Tileset 样式；
- Portal 与碰撞调试层；
- 人物元素；
- 与新地图相关的资源引用。

### 普通人物移动

只更新：

- 人物位置 Transform；
- 人物朝向；
- 人物移动状态；
- 人物动画相关表现属性。

地图静态内容创建后应尽量保持稳定，高频变化应集中为少量样式属性更新。

## 14. 状态原子应用

前端应完整应用同一版本的状态变化，再统一提交 DOM 更新。

不能出现：

- 地图已经切换，但人物仍属于旧地图；
- Tileset 已经更新，但瓦片仍使用旧索引；
- 人物位置来自新状态，但朝向仍来自旧状态。

DOM 不应直接订阅大量零散状态字段并在不同时间独立更新。

## 15. 地图切换渲染

地图切换需要形成一个完整的新场景，而不只是修改当前地图 ID。

流程为：

```text
运行时完成地图逻辑切换
        ↓
后端输出新地图完整客户端状态
        ↓
前端同步新地图状态
        ↓
前端通过资源接口加载缺失图片
        ↓
前端在当前场景外构建新 DOM 场景
        ↓
资源和 DOM 准备完成
        ↓
一次性替换当前场景
```

准备期间可以保持旧画面或显示纯色遮罩。第一阶段使用简单黑色遮罩即可。

## 16. DOM 不是状态来源

DOM 是状态的投影结果，不是数据存储或游戏状态来源。

不应：

- 读取 `offsetLeft` 或 `offsetTop` 作为玩家逻辑位置；
- 读取 `dataset` 作为权威地图或人物状态；
- 根据 CSS 动画是否结束决定碰撞或 Portal 是否发生；
- 直接修改 DOM 来表达游戏规则变化；
- 通过 DOM 反向修改后端权威状态。

所有游戏结果都应先由运行时产生，再通过状态同步进入前端。

## 17. 第一阶段性能边界

第一阶段地图规模较小，一个地图格子对应一个 DOM 元素是可接受的。

例如 `20 × 15` 的地图约有 300 个瓦片节点，加上人物、调试层和遮罩后，节点规模仍然较小。

第一阶段应遵守：

- 地图 Tile 创建后尽量不修改；
- 人物移动优先只更新 `transform`；
- 避免高频读取会触发布局计算的 DOM 属性；
- 一次状态更新中的 DOM 修改集中提交；
- 游戏视口裁剪场景外内容；
- 使用像素化图片渲染规则；
- 不在每个动画帧重新创建 DOM。

大地图虚拟化、Chunk、节点复用、Canvas 或 WebGL 不属于第一阶段。

## 18. 第一阶段渲染范围

第一阶段只实现：

- 一个固定游戏视口；
- 一个地图瓦片层；
- 一个玩家人物；
- Tileset 背景切片；
- 人物方向和最小行走动画；
- 人物位置平滑表现；
- Portal 和碰撞调试显示；
- 地图切换时的场景替换和遮罩；
- 通过资源接口加载 `tile.sheet` 和 `actor.sprite`。

第一阶段不实现：

- 前端完整读取或解析 FSDB；
- 多地图图层；
- 动态遮挡；
- 光照和 Shader；
- 粒子系统；
- 大地图虚拟化；
- 通用场景图；
- 多渲染后端；
- 复杂摄像机系统；
- DOM 与 Canvas 混合渲染。

## 19. 当前架构结论

第一阶段 DOM 渲染采用以下原则：

- 后端完整读取、校验和解释 FSDB；
- 后端持有地图状态和人物状态等权威游戏状态；
- 后端从权威状态生成面向前端的客户端可见状态；
- 前端不完整读取或解析 FSDB；
- 前端通过状态同步获得地图和人物的可渲染数据；
- 前端通过资源接口获取状态所引用的图片文件；
- 资源接口只交付图片资源，不代替状态同步；
- 后端不发送 DOM 操作或绘制命令；
- 前端通过“状态镜像 → DOM 场景投影 → DOM/CSS”生成最终画面；
- 权威状态、资源缓存和本地表现状态保持分离；
- 地图使用 DOM 网格表达，每个格子对应一个瓦片元素；
- Tileset 使用背景图片和背景位置显示具体 Tile；
- 人物使用独立 DOM 元素并通过 CSS Transform 表现位置变化；
- 人物动画帧和移动插值属于前端表现状态；
- 地图切换时准备完整新场景并原子替换；
- DOM 只作为状态的视觉投影，不作为游戏状态来源；
- 第一阶段优先验证正确性、可检查性和开发效率，不提前解决大地图和复杂渲染性能问题。
