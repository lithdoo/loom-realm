# 第一阶段 DOM 渲染与渲染状态

## 1. 文档目的

本文档记录 LoomRealm 第一阶段地图运行时原型的渲染方向。

第一阶段不使用 Canvas 或 WebGL，而是使用 DOM 与 CSS 将前端状态渲染为地图和人物画面。

本文档重点确定：

- 后端权威状态如何进入前端；
- 前端需要维护哪些渲染相关状态；
- 状态如何投影为 DOM 场景；
- 地图瓦片、人物移动和地图切换如何表现；
- DOM 渲染与游戏逻辑之间的边界。

具体组件框架、文件目录、CSS 命名和实现代码由开发阶段决定。

## 2. 总体渲染链路

LoomRealm 第一阶段采用以下渲染链路：

```text
FSDB 静态项目定义
        +
运行时权威状态
        ↓
客户端可见状态投影
        ↓
通用状态同步
        ↓
前端状态镜像
        +
静态资源缓存
        +
本地表现状态
        ↓
DOM 场景投影
        ↓
HTML 元素与 CSS
```

后端不发送 DOM 操作或绘制命令。后端只同步足以描述当前游戏结果的状态，前端负责将状态转换为 DOM。

因此不在通信协议中设计以下类型的命令：

```text
createElement
removeElement
setStyle
moveElement
drawTile
drawSprite
```

渲染方式属于前端实现细节，不属于运行时业务协议。

## 3. 状态与渲染结果的关系

同步状态不直接等同于最终 DOM。

前端需要在状态同步和 DOM 更新之间建立一层渲染投影：

```text
前端状态镜像
        ↓
DOM 场景投影
        ↓
DOM 节点与 CSS 属性
```

DOM 场景投影负责决定：

- 当前需要显示哪张地图；
- 地图需要创建哪些瓦片元素；
- 每个瓦片使用图集中的哪个区域；
- 人物元素位于何处；
- 人物当前面向哪个方向；
- 是否显示移动动画；
- 是否显示调试层或地图切换遮罩。

DOM 本身不负责解释游戏规则，也不参与碰撞和 Portal 判定。

## 4. 前端维护的三类数据

### 4.1 权威状态镜像

权威状态镜像是后端运行时同步到前端的可见状态副本。

第一阶段至少包括：

- 当前地图及其可渲染定义；
- 玩家使用的人物定义引用；
- 玩家逻辑位置；
- 玩家朝向；
- 玩家移动状态；
- 运行时状态版本；
- 地图是否正在切换或运行时是否发生故障。

前端不通过修改这份状态来改变游戏结果。

### 4.2 静态资源缓存

静态资源缓存保存已经加载的渲染资源，例如：

- `tile.sheet` 图片；
- `actor.sprite` 图片；
- 已解析的 Tileset 切分信息；
- 当前地图对应的瓦片 DOM 或样式缓存。

资源缓存不是游戏权威状态，可以由前端按需加载、释放或重新构建。

### 4.3 本地表现状态

本地表现状态只影响画面，不影响游戏规则，例如：

- 人物在两个逻辑格之间的像素插值进度；
- 当前人物动画帧；
- 摄像机或场景的视觉偏移；
- 地图切换遮罩；
- 资源加载状态；
- 调试图层开关。

基本边界是：

```text
玩家位于哪个逻辑格
    = 后端权威状态

人物当前绘制在两个格子之间的哪个像素位置
    = 前端表现状态
```

## 5. 客户端可见状态投影

后端内部状态不应直接完整序列化到前端。

后端应提供一份面向客户端渲染的状态投影，使前端能够重建当前画面，但不暴露与渲染无关的内部数据结构。

第一阶段的客户端可见状态概念上包括：

```text
当前地图
├── 地图尺寸
├── Tile 尺寸
├── Tileset 定义或引用
├── 地图瓦片数据
└── 地图内容版本

玩家
├── 人物定义或引用
├── 逻辑位置
├── 朝向
└── 移动状态

运行状态
├── 正常运行
├── 地图切换中
└── 故障
```

图片二进制不进入 JSON 状态。状态只提供资源引用，前端通过资源加载机制获取实际文件。

第一阶段在进入地图时，可以同步当前地图的完整可渲染定义；普通人物移动只同步动态状态变化。

## 6. DOM 场景结构

第一阶段建议将 DOM 场景划分为以下概念层：

```text
game viewport
└── game scene
    ├── tile layer
    ├── portal debug layer
    ├── actor layer
    └── overlay layer
```

各层职责如下：

- **game viewport**：固定显示区域并裁剪场景外内容；
- **game scene**：表示当前完整地图场景；
- **tile layer**：渲染地图瓦片；
- **portal debug layer**：仅在调试模式下显示 Portal 区域；
- **actor layer**：渲染玩家及后续动态人物；
- **overlay layer**：显示地图切换遮罩、加载状态和故障信息。

具体标签名称和 CSS 类名不在本文档中固定。

## 7. 地图瓦片渲染

第一阶段采用一个地图格子对应一个 DOM 元素的方式。

地图瓦片 DOM 根据以下数据生成：

```text
map.tile
    提供地图坐标和 tileIndex

tile.set
    提供 Tile 宽高、图集列数和图集资源引用

tile.sheet
    提供实际图片文件
```

每个瓦片元素使用图集图片作为背景，通过 `tileIndex` 计算对应的背景位置。

Tile 索引与图集坐标之间的规则由 FSDB 数据模型和 Tile 索引规则共同决定。

第一阶段优先使用 CSS Grid 表达完整矩形网格，因为它与按地图顺序保存的完整 `map.tile` 数据相匹配。

如果后续采用稀疏地图、多图层或任意位置对象，可以再评估绝对定位、视口裁剪或其他渲染策略。

## 8. 人物 DOM 表达

人物建议由两个视觉职责组成：

```text
人物位置容器
    表示人物在地图中的逻辑占用位置

人物精灵元素
    表示实际可见的角色图片和动画帧
```

人物位置容器按照地图坐标定位。

人物精灵元素可以高于或宽于一个 Tile，并以人物脚下位置作为视觉锚点。这样即使人物图片高度大于一个地图格，也不会改变人物的逻辑占用范围。

`actor.definition` 提供：

- 行走图资源引用；
- 单帧尺寸；
- 行列数量；
- 方向顺序；
- 其他必要的视觉定义。

`actor.sprite` 提供实际人物图片资源。

## 9. 人物移动表现

当运行时确认玩家从一个逻辑位置移动到另一个逻辑位置后，前端根据新的权威位置更新人物目标位置。

第一阶段优先采用：

> 格子逻辑移动，DOM 使用 CSS Transform 进行像素级平滑过渡。

CSS Transition、Web Animations API 或前端动画循环都只负责视觉表现，不能作为游戏逻辑完成的判据。

前端不能通过读取 DOM 的当前位置反推玩家逻辑位置。

正确的数据方向是：

```text
运行时权威位置
        ↓
前端状态镜像
        ↓
计算人物 DOM 目标位置
        ↓
CSS Transform 表现移动
```

而不是：

```text
DOM 当前位置
        ↓
反向决定游戏世界状态
```

## 10. 人物行走动画

运行时只需要同步人物的逻辑朝向和移动状态。

实际显示哪一个动画帧由前端决定。

人物动画帧属于本地表现状态，不属于权威游戏状态。

这一边界允许前端：

- 使用自己的动画速度；
- 在页面进入后台时降低或暂停动画；
- 根据性能情况调整动画更新方式；
- 在不改变运行时协议的情况下替换渲染实现。

## 11. 状态更新与 DOM 更新策略

前端不应在每次状态变化时重新创建整个地图 DOM。

第一阶段按静态内容和动态内容区分更新方式。

### 首次加载或地图切换

重新构建：

- 地图瓦片 DOM；
- 地图尺寸与 Tileset 样式；
- Portal 调试层；
- 人物元素；
- 与新地图相关的资源引用。

### 普通人物移动

只更新：

- 人物位置 Transform；
- 人物朝向；
- 人物移动状态；
- 人物动画相关表现属性。

### 调试状态变化

只更新对应调试层的可见性或样式。

地图静态内容创建后应尽量保持稳定，人物移动等高频变化应集中为少量样式属性更新。

## 12. 状态原子应用

前端应在一次渲染更新中完整应用同一版本的状态变化。

不能出现以下中间状态：

- 地图已经切换，但人物仍属于旧地图；
- TileSet 已经更新，但瓦片仍使用旧索引；
- 人物位置来自新状态，但朝向仍来自旧状态。

因此，状态镜像应先完成一次逻辑更新，再由 DOM 场景投影统一提交 DOM 变化。

DOM 不应直接订阅大量零散状态字段并在不同时间独立更新。

## 13. 地图切换渲染

地图切换需要形成一个完整的新场景，而不仅是修改当前地图 ID。

新场景至少需要准备：

- 新地图定义；
- 新地图瓦片数据；
- 新 Tileset 定义；
- 新地图需要的图片资源；
- 玩家目标位置和人物定义。

推荐的表现流程是：

```text
运行时进入地图切换状态
        ↓
前端收到新地图完整状态
        ↓
前端加载缺失资源
        ↓
前端在当前场景外构建新 DOM 场景
        ↓
资源和 DOM 准备完成
        ↓
一次性替换当前场景
```

准备期间可以保持旧画面或显示纯色遮罩。

第一阶段使用简单黑色遮罩即可，不需要设计复杂过场动画。

## 14. DOM 不是状态来源

DOM 是状态的投影结果，不是数据存储或游戏状态来源。

不应通过以下方式获得游戏状态：

- 读取元素的 `offsetLeft` 或 `offsetTop` 作为玩家位置；
- 读取 `dataset` 作为权威人物或地图状态；
- 根据 CSS 动画是否结束决定碰撞或 Portal 是否发生；
- 直接修改 DOM 来表达游戏规则变化。

所有游戏结果都应先由运行时产生，再通过状态同步进入前端。

## 15. 第一阶段性能边界

第一阶段地图规模较小，一个地图格子对应一个 DOM 元素是可接受的。

例如 `20 × 15` 的地图约为 300 个瓦片节点，加上人物、Portal 调试层和遮罩后，整体节点规模仍然较小。

第一阶段应遵守以下性能原则：

- 地图 Tile 创建后尽量不修改；
- 人物移动优先只更新 `transform`；
- 避免高频读取会触发布局计算的 DOM 属性；
- 一次状态更新中的 DOM 修改集中提交；
- 游戏视口裁剪场景外内容；
- 使用像素化图片渲染规则；
- 不在每个动画帧重新创建 DOM。

大地图虚拟化、Chunk、节点复用、Canvas 或 WebGL 不属于第一阶段。

## 16. 第一阶段渲染范围

第一阶段只实现：

- 一个固定游戏视口；
- 一个地图瓦片层；
- 一个玩家人物；
- Tileset 背景切片；
- 人物方向和最小行走动画；
- 人物位置平滑表现；
- Portal 和碰撞调试显示；
- 地图切换时的场景替换和遮罩。

第一阶段不实现：

- 多地图图层；
- 动态遮挡；
- 光照和 Shader；
- 粒子系统；
- 大地图虚拟化；
- 通用场景图；
- 多渲染后端；
- 复杂摄像机系统；
- DOM 与 Canvas 混合渲染。

## 17. 当前架构结论

第一阶段 DOM 渲染采用以下原则：

- 后端同步可恢复的客户端状态，不发送 DOM 或绘制命令；
- 前端通过“状态镜像 → DOM 场景投影 → DOM/CSS”生成最终画面；
- 权威状态、资源缓存和本地表现状态保持分离；
- 地图使用 DOM 网格表达，每个格子对应一个瓦片元素；
- Tileset 使用背景图片和背景位置显示具体 Tile；
- 人物使用独立 DOM 元素并通过 CSS Transform 表现位置变化；
- 人物动画帧和移动插值属于前端表现状态；
- 地图切换时准备完整新场景并原子替换；
- DOM 只作为状态的视觉投影，不作为游戏状态来源；
- 第一阶段优先验证正确性、可检查性和开发效率，不提前解决大地图和复杂渲染性能问题。
