# 文档分层与变更规则

> 层级：产品总览  
> 状态：Active / Normative  
> 稳定程度：稳定  
> 主要定义：文档层级、依赖方向、状态和迁移规则  
> 最近复核：2026-07-29

LoomRealm 仍处于早期设计阶段。文档必须允许上层设计调整后，有秩序地向下传播，而不是让多个专题文件互相覆盖。

## 1. 文档层级

```text
00-overview
    产品目标、范围、原则和文档治理
        ↓
10-architecture
    各系统的设计思想、职责和关系
        ↓
15-contracts
    跨系统和对外必须遵守的正式契约
        ↓
20-modules
    系统内部的模块拆分与深入设计
        ↓
30-implementation
    分包、依赖、测试和交付计划
```

### 00-overview

回答“为什么做、适用于什么、当前做什么、未来向哪里发展”。不记录具体包名、类名、消息字段或实现参数。

### 10-architecture

回答“系统如何划分、每个系统负责什么、状态归谁、系统之间如何协作”。可以描述核心流程，但不把示例 JSON 当作正式契约。

### 15-contracts

回答“两个独立实现如何互操作”。应包含 Schema、状态转换、顺序、错误、版本和兼容性语义。

### 20-modules

回答“一个系统内部拆成哪些模块、模块如何协作、有哪些不变量和失败边界”。模块设计不得扩大系统职责。

### 30-implementation

回答“当前仓库准备如何分包、按什么顺序实施、如何测试和发布”。实施结构可以变化，但必须遵守上层架构和契约。

## 2. 单向依赖

```text
Overview → Architecture → Contracts → Modules → Implementation
```

规则：

1. 下层文档可以细化上层结论，不能悄悄改变上层结论；
2. 下层发现设计问题时，应先修改对应上层文档；
3. 实施包结构不能反向成为产品架构；
4. 路线图和待办不能替代正式设计；
5. 同一结论只能有一个主要定义位置，其他文件通过链接引用；
6. 上层变化必须检查所有直接依赖文档；
7. 契约发生不兼容变化时必须提升协议版本或明确迁移过程。

## 3. 文档状态

| 状态 | 含义 |
|---|---|
| **Normative** | 当前必须遵守的范围或协议。 |
| **Active Design** | 当前有效的设计，允许随实现演进。 |
| **Draft** | 正在形成，不能作为稳定依赖。 |
| **Reference** | 背景、来源格式或外部资料。 |
| **Tracking** | 待办、开放问题和交付追踪。 |
| **Legacy** | 迁移期间保留的旧入口，不再新增主要定义。 |

## 4. 稳定程度

状态描述文档用途，稳定程度描述预计变化频率：

- **Stable**：变更需要明确设计评审；
- **Evolving**：方向明确，字段和流程仍可能调整；
- **Experimental**：用于验证，允许较大重构。

早期阶段允许 `Normative + Evolving`，表示当前实现必须遵守，但尚未承诺长期兼容。

## 5. 文档头部

新增设计文档应声明：

```text
层级：
状态：
稳定程度：
主要定义：
依赖：
被以下文档实现：
最近复核：
```

不适用的字段可以省略，但“层级、状态、主要定义、最近复核”应保留。

## 6. 变更传播

修改产品层时：

```text
更新产品总览
→ 检查所有系统架构
→ 检查受影响契约
→ 更新模块设计
→ 调整实施计划与测试
```

修改系统架构时：

```text
更新系统职责或关系
→ 检查跨系统契约
→ 检查相关模块
→ 调整分包和交付计划
```

只修改模块内部算法时，只要系统职责和外部契约不变，通常不需要修改上层文档。

## 7. 冲突解决

冲突按以下顺序处理：

1. 产品总览中的范围与长期原则；
2. 主题对应的系统架构文章；
3. 已声明为 Normative 的正式契约；
4. 模块设计；
5. 实施计划和路线图。

这里的顺序不是让上层文档覆盖协议事实，而是要求先修复上层与下层之间的矛盾。不能长期依赖“较新的提交自动优先”。

## 8. 旧文档迁移

本次重构采用渐进迁移：

1. 先建立新的分层入口和权威关系；
2. 旧详细文档暂时保留，作为模块和契约层的过渡资料；
3. 新文档不复制旧文档中的全部内容，而是明确主要定义位置；
4. 后续逐篇移动或重写旧专题，并修正交叉引用；
5. 旧路径最终改为 Legacy 提示或删除；
6. Git 历史用于追溯被替代方案。

迁移期间不得在新旧两处同时新增同一主题的主要定义。

## 9. 设计决策记录

重大决策应记录：

- 背景；
- 考虑过的方案；
- 当前决定；
- 原因和代价；
- 何时重新评估。

系统架构文档保存当前结论，决策记录保存形成结论的过程。

## 10. 当前迁移状态

新目录是推荐阅读入口。现有 `overview/`、`architecture/`、`contracts/`、`design/`、`game-package/`、`runtime/`、`fsdb/` 和 `roadmap/` 中的文件暂时保留为过渡资料。

后续迁移必须以不丢失有效设计、不中断文档站点内部链接为前提。
