# LoomRealm 总体架构

## 1. 文档目的

本文档描述 LoomRealm 当前已经确定的整体架构，只说明系统组成、职责边界和主要数据流，不展开协议字段、FSDB Schema、碰撞算法、DOM 结构或具体目录实现。

各模块的详细设计由对应专题文档负责。

## 2. 系统目标

LoomRealm 是一个以 FSDB 为项目数据基础、由权威运行时驱动、使用 Web 技术呈现，并能够运行在浏览器或桌面宿主中的 RPG 制作与运行平台。

第一阶段先完成一个可运行纵向切片：

- 使用 Pokémon Essentials v21.1 地图和素材作为兼容测试输入；
- 将输入转换为 LoomRealm 项目数据和运行时模型；
- 后端维护地图、人物、移动、碰撞和地图切换的权威状态；
- 前端根据状态和图片资源使用 DOM/CSS 渲染；
- Hostra 作为可选的 Electron 桌面宿主。

## 3. 架构原则

1. **项目定义与运行时状态分离**：FSDB 保存世界定义，运行时保存世界当前状态。
2. **运行时权威**：地图、人物位置、移动、碰撞和 Portal 结果由后端决定。
3. **前端只做投影**：前端发送归一化用户意图，并将客户端可见状态投影为 DOM。
4. **兼容逻辑集中**：Pokémon Essentials/RPG Maker XP 格式知识只存在于导出与兼容编译层。
5. **协议与部署分离**：相同状态和事件语义可以运行在本机 WebSocket、远程 WebSocket或 Worker 消息通道上。
6. **桌面宿主与游戏运行时分离**：Hostra 管理窗口和进程，不承载游戏业务状态。
7. **资源与状态分离**：状态同步描述如何渲染，资源接口负责交付图片内容。

## 5. 核心模块

### 5.1 项目数据层

项目数据层保存静态世界定义和资源引用，包括地图、Tile、人物和 Portal。

其职责是提供稳定、可校验、可由程序和 AI 修改的项目内容，不保存当前人物位置、移动过程或当前地图等运行时状态。

### 5.2 兼容导出与构建管线

兼容管线负责把 Pokémon Essentials v21.1 / RPG Maker XP 数据转换为 LoomRealm 可使用的项目内容。

它负责理解原始地图层、Tile ID、Tileset、Autotile、通行属性和 Priority。运行时核心和前端不直接解释原始 Ruby 数据或 `.rxdata` 文件。

### 5.3 Runtime Core

Runtime Core 是游戏规则和权威状态的核心。

它负责：

- 加载并编译项目数据；
- 创建运行时地图；
- 维护当前地图和人物状态；
- 处理方向意图、步进行走和碰撞；
- 处理 Portal 与地图切换；
- 生成面向客户端的可见状态。

Runtime Core 不依赖 DOM、Electron 或具体网络传输。

### 5.4 Runtime Server

Runtime Server 将 Runtime Core 暴露给客户端。

它负责：

- 承载通用状态同步和事件传递；
- 提供完整状态与增量状态；
- 提供图片资源访问；
- 提供 Web Client 静态文件和服务就绪检查；
- 处理连接、恢复和运行时错误边界。

### 5.5 Web Client

Web Client 是环境独立的普通 Web 应用。

它负责：

- 收集并归一化用户输入；
- 连接 Runtime Server；
- 维护客户端状态镜像；
- 加载状态引用的图片资源；
- 将地图和人物状态投影为 DOM；
- 管理不影响游戏规则的本地表现状态。

Web Client 不读取完整 FSDB，不判断碰撞，也不通过 DOM 反向生成权威状态。

### 5.6 Hostra 桌面宿主

Hostra 是 LoomRealm 的可选 Electron 桌面宿主。

它负责启动本地 Runtime Server、管理 BrowserWindow 和进程生命周期，并在 Runtime 就绪后打开 Web Client。

Hostra 控制 RPC 与 LoomRealm Runtime RPC 是两套独立通道。Hostra 不保存、代理或修改游戏权威状态。

## 6. 主要数据流

### 6.1 项目构建

```text
原始兼容项目
→ 导出与标准化
→ 校验和资源编译
→ LoomRealm FSDB 与资源
```

### 6.2 游戏启动

```text
项目入口
→ Runtime 加载和编译项目
→ 创建权威初始状态
→ 客户端获取完整状态
→ 客户端加载资源并构建 DOM 场景
```

### 6.3 用户操作

```text
用户输入
→ 前端归一化意图
→ Runtime 处理移动、碰撞和 Portal
→ 更新权威状态
→ 同步客户端可见状态
→ 前端更新 DOM 表现
```

### 6.4 资源加载

```text
客户端可见状态中的资源 Key
→ Runtime 资源接口
→ 图片内容与版本
→ 前端缓存和 DOM/CSS 使用
```

### 6.5 地图切换

```text
人物合法完成一步
→ Runtime 检测 Portal
→ 切换权威地图和人物位置
→ 发送新地图完整状态
→ 前端准备资源和新场景
→ 原子替换旧 DOM 场景
```

## 7. 状态边界

### 后端权威状态

- 当前地图；
- 人物稳定位置和朝向；
- 一步移动的起点、终点和时序；
- 碰撞结果；
- Portal 和地图切换结果；
- 可恢复的运行时故障状态。

### 前端表现状态

- DOM 当前像素位置；
- 人物当前动画帧；
- CSS 过渡进度；
- 图片加载状态；
- 调试层和界面临时状态。

### 静态项目数据

- 地图和 Tile 数据；
- Tileset、Autotile 和人物定义；
- 通行与 Priority 来源数据；
- Portal 定义；
- 资源文件和稳定资源 Key。

## 8. 部署形态

LoomRealm 保持同一套运行时语义，支持不同承载方式：

```text
桌面本地模式
Hostra → 本地 Runtime Server ← Web Client

浏览器本地模式
Web Client → Worker 传输适配 → 本地 Runtime

远程模式
Web Client → WebSocket → 远程 Runtime Server
```

部署差异不应改变项目模型、权威状态原则、状态同步语义或 DOM 渲染实现。

## 9. 第一阶段边界

第一阶段只验证：

- 两张 Pokémon Essentials v21.1 测试地图的导出和导入；
- 三层 Tile、普通 Tile、静态 Autotile、通行和 Priority；
- 一个玩家人物的四方向格子行走；
- 静态碰撞；
- 双向 Portal；
- Runtime 权威状态与客户端同步；
- DOM/CSS 地图和人物渲染；
- 浏览器运行和 Hostra 桌面运行。

第一阶段不包含完整地图编辑器、NPC、通用事件系统、战斗、存档、插件系统、多人同步和完整 Pokémon 业务逻辑。

## 11. 当前架构缺口

现有文档已经能够描述第一阶段运行时闭环，但仍缺少以下上层模块的正式设计：

1. **Maker 编辑器架构**：项目浏览、地图编辑、Inspector、命令事务、Undo/Redo 和预览协作尚无正式总体设计。
2. **兼容导出与构建管线**：目前散落在运行时文档中，尚缺独立的导出器、导入器和构建产物架构文档。
3. **项目与工作区模型**：`realm.project.json`、本地工作区配置、源项目路径和生成缓存的职责尚未完全冻结。
4. **协议与客户端状态 Schema**：通信原则已经确定，但完整状态、增量状态、事件和错误的正式契约尚未定义。
5. **资源生命周期**：资源 Key、内容版本、缓存失效、打包和重新导入规则尚未形成完整设计。
6. **校验、错误与诊断**：导入错误、项目错误、运行时错误、日志和编辑器定位之间的统一模型尚未定义。
7. **测试与兼容基准**：原创测试夹具、Golden Data、兼容回归和端到端测试结构尚未形成专题文档。
8. **构建、发布与安全模型**：桌面打包、远程部署、更新、远程鉴权和不可信项目数据边界尚未形成整体设计。
9. **持久化与世界状态**：第一阶段明确暂缓，但长期仍需定义存档、世界状态和项目静态数据之间的关系。
10. **扩展机制**：插件、用户自定义 Schema 和第三方能力尚未进入当前架构。

其中，最影响第一阶段实施的缺口是兼容构建管线、项目入口、状态 Schema、资源生命周期、错误诊断和测试基准。Maker 编辑器、持久化和扩展机制可以继续留在后续阶段。

## 12. 当前结论

LoomRealm 当前已经形成一条清晰的核心链路：

```text
兼容内容
→ FSDB 项目
→ 权威 Runtime
→ 状态与资源服务
→ 环境独立 Web Client
→ DOM/CSS 渲染
→ 浏览器或 Hostra 桌面宿主
```

后续设计应围绕这条链路补齐模块，而不是在专题文档中继续重复定义整体职责。
