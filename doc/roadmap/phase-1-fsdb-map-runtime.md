# 第一阶段：FSDB 驱动的地图运行时原型

## 1. 阶段定位

第一阶段不以“完成一个可用的 RPG Maker 编辑器”为目标，而是完成 LoomRealm 的第一个可运行纵向切片：

> 使用 FSDB 描述两张地图、一个玩家角色和双向传送关系；运行时读取项目数据后，玩家能够在地图中移动、受到静态碰撞约束，并通过传送区域切换地图。

这一阶段用于验证 LoomRealm 最基础的数据驱动链路：

```text
FSDB 项目数据
  → 数据读取与校验
  → 领域模型转换
  → 地图运行时实例化
  → 输入处理
  → 玩家移动
  → 碰撞检测
  → Portal 触发
  → 目标地图加载
```

第一阶段成功的标准不是功能数量，而是证明地图内容确实由 FSDB 驱动，而不是把硬编码数据换一种文件格式保存。

---

## 2. 核心目标

第一阶段只实现以下四项核心能力：

1. 从 FSDB 加载地图定义。
2. 玩家角色可以进行上下左右四方向移动。
3. 玩家角色不能穿过被标记为阻挡的地图格子。
4. 玩家进入 Portal 区域后，可以切换到另一张地图并出现在指定位置。

测试项目至少包含：

- 两张可往返的地图；
- 一个玩家角色；
- 每张地图的静态碰撞数据；
- 一对双向 Portal；
- 每张地图的默认出生位置。

---

## 3. 阶段范围

### 3.1 地图加载

第一阶段地图系统只需要支持：

- 固定网格地图；
- 统一的 Tile 尺寸；
- 一个基础地面层；
- 一份静态碰撞数据；
- Portal 传送区域；
- 两张测试地图；
- 通过地图 ID 加载指定地图。

第一版不要求实现 RPG Maker XP 的 Autotile 规则。地图甚至可以先使用颜色块或原创占位 Tile 渲染，只要数据结构和加载流程成立。

### 3.2 玩家移动

第一阶段玩家控制只支持：

- 单一玩家角色；
- 键盘输入；
- 上、下、左、右四方向；
- 固定移动速度；
- 网格碰撞或简单 AABB 碰撞；
- 面向方向与行走动画的最小状态。

移动系统需要与玩家图片尺寸解耦。角色的视觉高度可以超过一个 Tile，但碰撞区域应以脚下格子或独立碰撞盒为准。

### 3.3 静态碰撞

第一阶段碰撞只处理：

- 地图边界；
- 不可通行格子；
- 玩家与静态地图阻挡之间的碰撞。

不处理动态实体碰撞、推箱子、斜坡、高低层、像素级碰撞和复杂物理效果。

### 3.4 地图跳转

Portal 至少需要表达：

- Portal 所在地图；
- Portal 的触发区域；
- 目标地图；
- 目标位置；
- 可选的目标朝向。

触发后的最小流程：

1. 暂停当前地图输入或更新；
2. 校验目标地图和目标坐标；
3. 卸载当前地图运行时实例；
4. 加载并实例化目标地图；
5. 将玩家放置到目标位置；
6. 恢复输入和更新。

第一阶段不要求淡入淡出、加载画面、过场动画或复杂异步资源预载。

---

## 4. 明确不属于第一阶段的内容

以下功能全部延后，不应进入第一阶段的完成条件：

- 完整可视化地图编辑器；
- Tileset 或素材库管理器；
- RPG Maker XP Autotile；
- 多层混合、视差背景和光照；
- NPC 与动态实体；
- 对话系统；
- 通用事件系统；
- 开关、变量与自开关；
- 背包、道具、技能与战斗；
- 存档和世界状态库；
- Maker Core DB、Library DB 和多库依赖；
- 用户自定义 Schema；
- 插件系统；
- 通用跨库引用；
- 寻路、队伍跟随和 AI；
- 八方向移动、加速度和复杂物理；
- 网络同步和多人游戏。

第一阶段尤其不应同时承担完整地图编辑器。否则会额外引入画布交互、缩放、图层管理、选择、Inspector、Undo/Redo、脏状态和编辑态同步等大量工作。

---

## 5. 实施顺序

第一阶段内部建议分为两个连续子里程碑。

### 5.1 1A：运行时技术探针

先使用硬编码数据验证：

- 渲染循环；
- 输入处理；
- 玩家矩形或占位精灵移动；
- 静态墙体碰撞；
- 两个硬编码场景之间切换；
- 坐标系统和相机基本行为。

这一子里程碑只用于降低技术风险，不构成第一阶段最终交付。

### 5.2 1B：FSDB 数据驱动

将 1A 中的硬编码地图数据替换为 FSDB：

- 读取 FSDB；
- 校验 Schema；
- 转换为领域模型；
- 加载两张地图；
- 加载碰撞数据；
- 加载 Portal；
- 完成双向地图切换。

第一阶段最终交付必须完成 1B。

---

## 6. 第一阶段 FSDB 边界

第一阶段只使用一个项目数据库：

```text
[FSDB]project/
```

暂不实现 Maker Core、Library、World State 或 Workspace 等分库。

### 6.1 推荐的最小目录

```text
[FSDB]project/
├── [struct]map/
│   ├── town.json
│   ├── house.json
│   └── .info.meta
│
├── [group]map-grid/
│   ├── town.jsonl
│   ├── house.jsonl
│   ├── .info.meta
│   └── .desc.meta
│
├── [extend]map-portal/
│   ├── town-to-house.json
│   ├── house-to-town.json
│   ├── .info.meta
│   └── .extend.meta
│
└── [resource]map-assets/
    ├── test-tileset.png
    ├── test-player.png
    └── .desc.meta
```

该结构是第一阶段的起点，不代表最终项目模型已经冻结。

### 6.2 地图定义示例

```json
{
  "name": "Town",
  "width": 20,
  "height": 15,
  "tileSize": 32,
  "defaultSpawn": {
    "x": 3,
    "y": 5,
    "direction": "down"
  }
}
```

地图文件名作为地图 key，例如：

```text
[struct]map/town.json
```

### 6.3 地图格子示例

```jsonl
{"x":0,"y":0,"tile":"grass","blocked":false}
{"x":1,"y":0,"tile":"wall","blocked":true}
{"x":2,"y":0,"tile":"grass","blocked":false}
```

第一阶段可以在同一条格子记录中同时保存 Tile 与 `blocked`，避免为了架构纯度过早拆分地面层和碰撞层。后续确认编辑需求后再决定是否拆表。

### 6.4 Portal 示例

```json
{
  "sourceMapId": "town",
  "targetMapId": "house",
  "sourceArea": {
    "x": 8,
    "y": 5,
    "width": 1,
    "height": 1
  },
  "targetPosition": {
    "x": 4,
    "y": 7
  },
  "targetDirection": "up"
}
```

对应 `.extend.meta`：

```jsonl
{"field":"sourceMapId","struct":"map","desc":"Portal 所在地图"}
{"field":"targetMapId","struct":"map","desc":"Portal 目标地图"}
```

`sourceArea` 和 `targetPosition` 是 Portal 关系本身的属性，不需要拆成独立实体。

---

## 7. 运行时架构边界

运行时代码不应在各个系统中直接访问 FSDB 文件。第一阶段建立最小适配层：

```text
FSDB Reader
  → Map Repository
  → Map Definition
  → Runtime Map
```

建议的领域接口：

```ts
interface MapDefinition {
  id: string;
  name: string;
  width: number;
  height: number;
  tileSize: number;
  defaultSpawn: SpawnPoint;
  cells: MapCell[];
  portals: MapPortal[];
}

interface MapCell {
  x: number;
  y: number;
  tile: string;
  blocked: boolean;
}

interface MapPortal {
  id: string;
  sourceMapId: string;
  targetMapId: string;
  sourceArea: Rect;
  targetPosition: Point;
  targetDirection?: Direction;
}
```

该边界保证未来调整 FSDB 表结构时，只需修改 Repository 或数据编译层，而不是重写移动、碰撞和场景系统。

---

## 8. 测试素材规格

第一阶段采用 RPG Maker XP / Pokémon Essentials 风格的素材尺寸作为测试约定，但 LoomRealm 不承诺永久绑定该格式。

### 8.1 逻辑画面

| 项目 | 第一阶段规格 |
|---|---:|
| 逻辑分辨率 | 512 × 384 px |
| Tile 尺寸 | 32 × 32 px |
| 默认可视区域 | 16 × 12 Tile |
| 缩放方式 | 1×、2×、3×整数倍 |
| 纹理过滤 | Nearest Neighbor |

渲染时应禁用图片平滑，避免像素素材产生模糊。

### 8.2 Tileset

第一阶段 Tileset 建议：

- 固定宽度：256 px；
- 每行 8 个 32 × 32 Tile；
- 高度为 32 的整数倍；
- 测试文件可使用 256 × 512 px；
- 暂不实现 Autotile。

### 8.3 玩家行走图

第一阶段采用：

- 4 列动画帧；
- 4 行方向；
- 方向顺序：下、左、右、上；
- 推荐单帧：32 × 32 px；
- 推荐整图：128 × 128 px。

但资源定义不应将单帧固定写死为 32 × 32。应显式保存：

```json
{
  "image": "test-player.png",
  "frameWidth": 32,
  "frameHeight": 32,
  "columns": 4,
  "rows": 4,
  "directionOrder": ["down", "left", "right", "up"]
}
```

这样未来也可以支持每帧 32 × 48 等更高角色素材。

### 8.4 碰撞和视觉分离

角色视觉图片不应直接作为碰撞边界。第一阶段至少应做到：

- 角色锚点位于底部中央；
- 碰撞盒与图片尺寸独立；
- 高于一个 Tile 的角色头部可以超出当前格子；
- 碰撞逻辑以脚下位置或独立碰撞盒判断。

---

## 9. 素材版权约束

宝可梦原始图像、角色、名称和设计不应提交到公开的 `loom-realm` 仓库。

推荐约定：

```text
assets-test/
├── pokemon/       # 仅本地测试，加入 .gitignore
└── placeholder/   # 原创或具有明确授权，可提交
```

公开仓库应只包含：

- 原创占位 Tile；
- 原创占位角色；
- 明确允许再分发的测试资源；
- 资源来源和许可证说明。

第一阶段可以在本地临时测试兼容素材，但项目的自动化测试和公开演示不能依赖未经授权的宝可梦素材。

---

## 10. 数据校验要求

第一阶段至少检查：

- 地图宽高必须为正整数；
- `tileSize` 必须为正整数；
- 地图格子坐标不能越界；
- 同一地图不能出现重复格子坐标；
- Portal 的源地图必须存在；
- Portal 的目标地图必须存在；
- Portal 的触发区域不能越出源地图；
- Portal 的目标位置不能越出目标地图；
- 默认出生位置不能越界；
- 玩家不能出生在不可通行格子；
- Portal 目标位置不能位于不可通行格子。

无效数据必须产生明确、可定位的错误信息，不能静默忽略或导致运行时随机失败。

---

## 11. 验收标准

第一阶段完成必须同时满足以下条件：

1. 项目中存在两张由 FSDB 描述的测试地图。
2. 启动时可以通过地图 ID 加载初始地图。
3. 玩家可以使用键盘进行上下左右四方向移动。
4. 玩家不能进入被标记为阻挡的格子，也不能越出地图边界。
5. 玩家进入 Portal 触发区域后可以切换到目标地图。
6. 地图切换后，玩家出现在 Portal 指定的目标坐标和朝向。
7. 玩家可以从目标地图返回原地图，形成完整双向闭环。
8. 修改 FSDB 中的地图尺寸、Tile、碰撞或 Portal 位置后，不需要修改运行时代码。
9. 无效地图引用、越界坐标和错误出生点会产生明确错误。
10. 地图读取、领域模型、运行时实例和渲染逻辑之间保持清晰边界。
11. 公开仓库中的测试素材均为原创或具有明确授权。
12. 至少具备针对地图解析、Portal 引用和越界校验的自动化测试。

---

## 12. 第一阶段交付物

第一阶段应交付：

- 最小可运行 Web Demo；
- 两张测试地图；
- 一个可移动玩家角色；
- 静态碰撞；
- 双向地图跳转；
- 一份符合 FSDB 规范的测试项目数据；
- 地图数据校验器；
- 地图领域模型与 Repository；
- 最低限度的自动化测试；
- 原创或明确授权的测试素材；
- 更新后的开发文档。

---

## 13. 延后决策

第一阶段完成前，不冻结以下设计：

- 最终地图分表方式；
- Tile 与碰撞是否永久存放在同一个 `[group]`；
- 地图编辑器数据模型；
- 用户自定义 Schema；
- 多数据库与跨库引用；
- 世界定义和世界状态的完整拆分；
- 插件数据注册机制；
- 通用事件系统；
- 最终渲染引擎和资源打包格式。

这些问题应根据第一阶段暴露出的真实需求再做决策，避免在没有运行验证的情况下过度设计。

---

## 14. 阶段完成定义

当开发者可以只修改 FSDB 数据和测试资源，在不修改移动、碰撞和地图切换代码的情况下改变地图布局、阻挡区域和传送目标，并且双地图 Demo 稳定运行时，第一阶段视为完成。
